## 6.4 自适应调度

### 表 5 — 负载 `mixed_burst`

| 配置 | 达标率 | 达标吞吐 (req/s) | 达标吞吐 (tok/s) | TTFT P99 | TPOT P99 | **stall P99** | 未完成率 | 控制器决策数 | 冷却跳过数 | 恢复次数 | chunk 建议/生效 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 静态默认参数 | - | - | - | - | - | - | - | - | - | - | - | - |
| 静态最优参数 | - | - | - | - | - | - | - | - | - | - | - | 来自 E2 的最优点 |
| 自适应 | - | - | - | - | - | - | - | - | - | - | - | 主指标是达标率与达标吞吐，不是平均时延 |

> 三个达标口径分列（`slo_satisfaction_rate` / `slo_goodput_req_s` /
> `slo_goodput_tok_s`），不合并成一列 `Goodput`——它们不是同一个量。
> 「冷却跳过数」对应 `n_skipped_cooldown`：若它恒为 0，说明冷却窗口比决策节拍
> 还短，这个参数是死的（扫它不会有任何效果）——必须报出来，而不是当成"冷却正常"。

待填（E7）。必须回答四个问题，缺任何一条这个方案都没被真正评估：

1. 自适应相对静态最优是否仍有差距；若人工调参能轻松打败自适应，如实报告。
2. **建议值是否兑现**：`meta.controller_effect` 里 `chunk_requested` 与
   `chunk_effective` 的差额必须为 0。不为 0 说明决策被某个闸门静默压回了，
   此时"自适应有效/无效"的任何结论都不成立（先修 harness）。
3. **恢复路径是否走过**：`n_decisions_recover > 0`，且负载回落后回到配置初值。
   若恒为 0，控制器就是一根只会收紧的棘轮，"负载变化时自适应"这个主张无从谈起。
4. **信号是否真的参与了**：`controller_trace[*]._unavailable_signals` 里
   缓存命中率与可用显存是否为空。离线路径上它们必然为空（`--dry-run` 无显存读数），
   因此**信号闸门只能在真机上被真正评估**；在真机 telemetry 上可用
   `replay_decisions` 复放验证，不必重跑基准。
