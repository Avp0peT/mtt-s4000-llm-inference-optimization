### 1.4 贡献结构（规范第 17 节）

> **2026-09-26 重写**。旧版把"batching × Prefix Cache × Prefill 分块的联合优化"当贡献 ——
> **已废弃**，原因有两条：① 前缀缓存/量化已明确**不在研究范围内**
> （见 `paper/experiments.md` §7 的"已收掉"表）；② 成本预测 / deadline / 自适应 chunk
> **已有相近工作**（最接近的 SLOWeave, arXiv:2609.07883）⇒ **这些机制本身不宜作为算法贡献**。

**本文贡献不是**"我们启用了前缀缓存/量化/更大的 batch"，**也不是**"我们提出了一个
成本模型控制器 + deadline + 自适应 chunk"（前两类都已存在、第三类最接近的方法已占先）。

**贡献是**（每条都指向已落地的工具与登记行）：

1. **Contribution 1 — 平台与执行特征**：MTT S4000 上**服务协议**（逐步 sync + KV 真实生长）
   下的逐步成本画像；块 A（快态平台）与块 B（服务协议）**分开采、分开报**，
   并给出"不能只拟合快态最小值"的实据。
2. **Contribution 2 — 成本模型的失效归因**（本研究的核心增量）：
   证明**同一个模型**的"留出误差"可以从 **1.77% 变到 95.25%**；
   **真因是训练集的秩/覆盖不足** ⇒ 给出**秩保证划分**与**覆盖诊断**；
   并证明**v1 网格里秩 3 根本达不到** ⇒ "扩网格"由此成为**必要条件**（而不是调参）。
   ⚠️ **还要含"执行状态描述"那一半**：标定的 `prefill_tok` 与 harness 的 `tokens_prefilled`
   语义差约 `batch` 倍 —— 这一类错**不会因加密网格自愈**（见 §4.3）。
3. **Contribution 3 — 判据口径与现有特征的不足**：真实服务步里存在一笔**按序列**的额外开销
   （`host` 侧），而模型只预测**前向**、deadline 约束的是**整步** ⇒
   口径错直接造成 **D1 = 84.6%**（"预测可行、实际超时"）。
4. **Contribution 4 — 预测失配如何变成调度代价**：把
   **误差 → 错误决策（D0 候选是否被用上 / D1）→ 保守等待（D2）→ 服务收益（D3）**
   做成**可复算的证据链**，并给出**适用边界**（哪些负载区它能改善、哪些区它没有收益甚至更差）。

**明确不主张**：① 某个新控制器算法；② 在本平台上优于最接近方法；
③ 跨平台普适或芯片固有机制。

## 4. 成本模型失效分析（阶段二 · **核心增量**）

> 本节的**内容**写在 `paper/failure_analysis.md`（**三层标注**：【事实】/【解释】/【假设】，
> 并显式列出"刻意不写"的四项）。本节只列骨架，避免两处各写一份：

- 4.1 「有限标定数据」这一半：**划分规则**（同一模型 1.77% ↔ 95.26%）、
      **秩不足**是真因、秩保证划分的效果、v1 网格达不到秩 3、2×2 解耦（划分 ≈89pp / 网格 ≈5.7pp）、
      覆盖率与代价的取舍曲线
- 4.2 失效归因表：**逐类给证据**（训练秩不足 / 覆盖缺口 / 表达力不足 / 测量波动）
- 4.3 「执行状态描述」这一半：`prefill_tok` 的**语义差**（每条 vs 全步总量，差约 `batch` 倍）
      —— 它与 4.1 **性质不同**：不会因加密网格而自愈
- 4.4 两个**方向相反**的系统误差：纯 decode 步**低估**（漏 host）vs prefill 重步**高估 ~b 倍**；
      以及"两者都不在'模型精度'那一个数字里"这一点
- 4.5 **待验证假设**（5 条，见 `failure_analysis.md` §4.5）——**不得**当前提用

## 5. 针对性改进与消融（阶段三）

- 5.1 **逐步按序列的 `host` 开销项**（实测 b8：整步 130.52 = 前向 104.79 + host 25.25）
      —— ⚠️ 它**不进模型**，进的是**判据**（`预测整步 + host ≤ 每步预算`）
- 5.2 **秩保证划分 + 覆盖诊断**（对照：哈希划分）
- 5.3 **标定语义修正**（`uniform` → `real_mixed`；新增模型版本，不覆盖旧模型）
- 5.4 **候选集**：`chunk_size_min/max` 是**可动范围**、`candidate_chunks` 是**评估点**；
      两者的分工与"改下限不会自动新增中间点"这个实现事实
- 5.5 **实现约束与闭环契约**（每条都对应一个**不会报错**的失效，因此必须显式设计与验证）：
  - **运行期上限只有一处权威**：分块策略读 `chunk_policy.ChunkLimits`，
    而不是静态配置值（否则"日志显示调大、额度未变"）
  - **双向可逆**：收缩是防御、放大是恢复；**恢复上限 = 配置初值**而非参数上界
    （只有收缩没有恢复的控制器是棘轮）
  - **可行**：`chunk_size <= max_batched_tokens`
  - **信号要么可信、要么显式为 `None`**：未测信号不参与决策但必须显形
    （缓存关闭时命中率是 `None` 而**不是** `0.0`）
- 5.6 **消融清单**（预注册见 `EXPERIMENTS.md` 第 15 步节）：
      只调 chunk / 只调 budget / 去掉误差裕量 / 换信号 / **去掉 host 项**

支撑要求：每个改进都要有**单变量**的消融对照；`full` 与各消融**恰好差一处**（由用例强制）。
