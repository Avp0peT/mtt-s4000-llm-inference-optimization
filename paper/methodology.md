# 方法论

本文件定义本研究的测量与推断规则。**它先于实验存在**，用来防止「先有数字、
再补方法」这种事后合理化。

---

## 1. 指标定义（唯一口径）

| 指标 | 定义 | 采样点 | 用途 |
| --- | --- | --- | --- |
| TTFT | 请求到达 → 首 token 返回 | 首 token 事件 | 交互体验；受排队与 prefill 影响 |
| TPOT | decode 相邻 token 的平均间隔 | 每次 decode 步 | 生成流畅度；受批组成与带宽影响 |
| TPOT stall | 单请求自身 token 间隔的 **P99** | 每次 decode 步 | 卡顿程度；尾延迟优化的主证据 |
| E2E | TTFT + TPOT × (gen_len − 1) | 请求完成 | 端到端验收 |
| Throughput | 输出 token 数 / 计时窗口（tok/s） | 整轮 | 吞吐效率，必须同时报并发度 |
| 达标率 `slo_satisfaction_rate` | 满足 SLO 的请求数 / **全部提交的请求数** | 整轮 | 自适应策略的主目标之一 |
| 达标吞吐 `slo_goodput_req_s` | 满足 SLO 的请求数 / 测量秒数 | 整轮 | 单位时间内的有效服务量（按请求） |
| 达标吞吐 `slo_goodput_tok_s` | 满足 SLO 的请求的输出 token / 测量秒数 | 整轮 | 单位时间内的有效服务量（按 token） |
| Cache Hit Rate | 复用 token / prompt token | 整轮 | 前缀缓存收益 |

**达标口径刻意拆成三个数，不用 `goodput` 这一个名字。** 这个名字会同时被读成
"达标比例"和"达标吞吐"，而两者是不同的量；混名之后没人知道表里那一列到底在说什么。
三者不可互相替代：一个策略可以让达标率上升而达标吞吐下降（把请求切得更碎、
每次都能达标但单位时间干得更少）。未配置 SLO 时三者一律记 `None`——**不写 0**：
0 是"测出来一个都没达标"，`None` 是"这轮没设 SLO、根本无从判定"。

三条硬性要求：

1. **一律报 P50 / P90 / P99**，不得只报均值。均值会被大量快请求掩盖尾延迟。
2. **TPOT 与 TPOT stall 必须并列报告**。二者回答不同的问题：
   TPOT 回答"整体流畅度"，stall 回答"最坏那次停顿有多长"。
   长 prompt 阻塞造成的数秒级停顿会被 `gen_len` 除开、在 TPOT 均值里几乎不可见——
   只用均值会导致「明明修好了卡顿，却因为均值没动而判定优化无效」。
   本项目在一次实验中发现同一 run 的 TPOT P99 为 74 ms 而 stall P50 为 968 ms，
   相差一个数量级，这就是必须分列的直接证据。
3. **E2E 与「完成时刻 − 到达时刻」必须对得上**。差值是计时口径 bug 的探针，
   实现中以 `accounting_error_ms` 落地并在产物中记录 P99。
   参考点必须是**到达时刻**：闭环负载下请求在获得客户端容量时才产生，
   用排队时刻做参考点会引入恒定偏差。
4. **口径一旦变更，必须在 `RESEARCH_LOG.md` 中声明并标注影响范围**。
   中途偷改口径是本项目最需要防范的自我欺骗形式。
5. **缺失必须是 `None`，不得填 0。** 0 是"测出来是 0"，`None` 是"没测到 / 未发生"。
   例如前缀缓存**关闭**时命中率记 `None`（这个信号根本不存在），
   开启了但一次没命中才记 `0.0`（测到了，结果就是没命中）。
   混同两者会让"还没做"看起来像"做完了、结果是 0"。
6. **时延分位只统计成功请求**，因此必须与未完成率一起看：
   最慢的那批请求往往根本没跑完，只报分位会系统性高估服务质量。
   同理，`n_failed = 0` 在模拟路径上的含义是"这条路径产生不出失败"，
   而不是"测过、没失败"——不要把它读成后者的证据。

## 2. 测量纪律

- **预热在计时窗口之外**：按时间预热（默认 ≥30s）而非固定迭代数。
  未完成的预热表现为「前若干次迭代系统性偏慢」，会被误读成优化收益。
- **计时窗口内不做**：JIT 编译、图捕获、显存分配、日志格式化。
- **抖动分类**（三类，处置方式不同）：
  1. 预热未完成的单调漂移 → 修测量（延长预热）
  2. 单次停顿 outlier → 修判据（用稳健统计量）
  3. 系统性降频（热/功耗墙）→ 修实验设计（降负载或记录温度）
- **离散度用稳健 CV** = 1.4826 × MAD / median。普通 CV 对单个 outlier 毫无抵抗力，
  会让人误以为系统不稳定。

## 3. 对照设计

- **单变量**：一次只改一个维度。组合优化单独登记为一条实验，
  不允许把两个变量的收益混算成一个数字。
- **可比性前置检查**：工作负载、成功请求数、SLO、环境指纹必须一致；
  不一致时 `metrics.compare` 会输出 warning，此时**不得**报告差值。
- **模拟与实测不混用**：`--dry-run` 的产物带 `dry_run: true`，
  聚合时默认排除。模拟结论可以指导设计，不能进入性能结论。

## 4. 推断规则

设 `noise` 为两次 run 的稳健 CV 的最大值，则：

- 差值 |Δ| ≤ noise → 判为 **inconclusive（测不出结论）**，需增加重复次数。
  这是合法状态，必须与「测出了坏结论」区分开表述。
- 所有观测指标的 P99 均改善且 |Δ| > noise → **positive**
- 所有观测指标的 P99 均恶化且 |Δ| > noise → **negative**
- 部分改善、部分恶化 → **mixed**，需按目标函数加权后再判断

**重复次数 < 3 的组不产生结论**。这一条没有例外——
它拦掉的是一大类「看起来显著、重跑就消失」的结果。

## 5. 模拟路径的定位与限制

`--dry-run` 用一阶设备模型驱动全链路，其唯一目的是：

1. 验证 harness 与策略接线（跑得通、账目自洽、控制器不振荡）
2. 在无硬件环境下做设计空间的粗筛

限制（必须写进论文的 Threats to Validity）：

- 模型假设 prefill 算力受限、decode 带宽受限，且都是线性关系。
  真实硬件的算子效率、显存层次、图模式收益都未被建模。
- `runtime` 段的开关（量化、图模式）在模拟路径下**完全不生效**。
  用模拟评估这些维度得到「零差异」是预期的，不是发现。
- 因此：模拟数值不得与实测数值放在同一张表或同一张图上比较。

## 6. 可复现性要求

一次 run 的产物必须包含：完整配置快照、环境指纹、逐请求指标、时间序遥测、
代码版本。缺任意一项，该 run 的结果不能进入结论——因为无法判断它是在什么
条件下得到的。

## 7. 已知的方法论弱点（诚实清单）

1. 工作负载由参数化生成器产出，与真实线上流量的重尾分布有差距。
2. 单卡单机结论对多卡并行场景（通信开销占比）外推风险高。
3. 控制器使用 P90 作判据，对突发尖峰的反应可能偏慢。
4. 前缀缓存的收益上限由模拟模型给出，与真实 KV 块的物理布局可能存在偏差，
   需要在真机上做一次命中率对齐验证。
