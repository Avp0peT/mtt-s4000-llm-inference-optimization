## 2.1 推理两阶段与各自瓶颈

自回归推理分 prefill（一次前向吃下整段 prompt，产出 KV）与 decode（每步 1 token）。
两者的资源特征不同：prefill 偏算力、decode 偏带宽与 KV 访问。
在同一张卡上把两者混步执行，就产生了"这一步给 prefill 多少 token"的取舍 ——
这正是本文所有调度决策的**被控量**。

本项目在该平台上实测到的执行特征（§3）有两条直接影响建模：
① 一步的成本是**分组加和**的（`real_backend` 按每个序列新增 token 数分组串行前向），
batch 是**次线性**主项（b1 59.9 → b8 109.2 ms，**1.82×**）；
② 一步里除前向之外还有一笔**按序列**的 host 侧开销（打包 / mask 组装 / 取回），
b8 时约 **25 ms**，与"每步预算"同量级 —— 而模型只预测前向。

## 2.2 分块预填充与调度（本文的对照对象）

* **Sarathi-Serve**（OSDI '24）提出分块预填充 + stall-free 调度，是本文**固定分块静态基线**
  的直接来源。本文的静态臂即按它的思路取"固定 chunk / 固定单步 token 预算"。
  ⚠️ 其开源实现自述为**研究原型**（vLLM fork，功能不完整）⇒ 本文只借用其**调度规则**，
  不声称"复现了完整系统"。
* **DistServe**（OSDI '24）给出 **goodput** 的定义与讨论口径，并量化 prefill-decode 干扰；
  其**多设备分离**架构不在本文范围内，但 goodput 的口径被本文沿用
  （`paper/methodology.md` §1；本文进一步把它拆成三个不可互相替代的数）。

## 2.3 自适应分块与成本预测（最接近的一族）

* **SLOWeave**（arXiv:2609.07883）—— **与本文第三臂最接近**：成本预测 + next-token deadline +
  自适应 chunk。其方法选择"预测能在最早活跃 decode 的 next-token deadline 前完成的
  **最大** prefill chunk"，对**单调迭代成本模型**做**对数时间搜索**，且**无需按负载调** chunk size；
  作者强调方法**刻意收窄**（不改编排路径、不改 kernel）。
  评测为 event-driven 模拟器 + iteration-level GPU runtime，四类负载（chat / mixed / long / **bursty**），
  TPOT 目标 10/25/50 ms、TTFT SLO 1000/1500/5000 ms；25 ms 目标下 goodput 比最强固定 chunk 基线
  **+39%（mixed）/ +38%（long）**，10 ms 目标下升至 **3.3× / 2.4×**。
  本项目实现了它的算法作为**对照臂**（`src/ascend_opt/slo_weave.py`），
  因此本文**不**把"成本模型 + deadline + 自适应 chunk"当作算法贡献。
  ⚠️ 两点必须并记：① 它的 artifact 在论文中**声明存在**，但本轮检索**未找到可访问仓库**
  ⇒ 我们的实现属"按论文写的 policy 参考版本"，**不得**冒称完整复现；
  ② 作者自述局限——真实迭代成本**可能非平滑**（kernel 边界、张量并行通信、显存压力、前缀命中）
  ⇒ **标定漂移**需要更广泛部署研究；**持续过载时严格 TPOT 目标可能没有安全的 prefill 预算**。
* **DRLServe**（ECAI 2025）代表**学习型**路线（RAPC / TAPPO，把推理建模为 MDP）。
  本文不做强化学习，但把它列为"同族的另一条路"，用以说明"自适应 chunk"这一族已有多条实现路径。

## 2.4 与本文的差异

既有的这一族工作，评价重点在"**机制是否有效**"（吞吐/延迟改进了多少）。
本文把重心前移一格：**在机制给定的前提下，预测可靠性由什么决定**。
具体差异：

1. 我们报告"**留出误差在划分规则未固定时没有可比性**"这一现象，并给出真因（秩 / 覆盖不足）
   —— 这是**评估协议**层面的事，与机制无关；
2. 我们区分失效的**两半**（有限标定数据 / 执行状态描述），并指出后者**不会因加密标定网格而自愈**；
3. 我们用 **D0/D1/D2/D3** 把"预测失配"接到"服务代价"，而不是只看端到端指标
   —— 因为端到端指标会把"没被用上"与"用了没用"混在一起；
4. 我们给出的**不是**"这类机制在本文平台上更好"，而是**它的失效边界与代价形状**——
   §7 如实报告：截至目前，收益侧证据**尚未建立**。

⚠️ **不得**写成"我们首次发现 / 首次提出"任何一项 —— 上述现象在别处可能已被观察到，
本项目没有做过系统的相关工作普查（`SOURCES.md` 仍有多条 `unverified`）。
