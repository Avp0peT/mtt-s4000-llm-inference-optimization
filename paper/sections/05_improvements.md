# 5 针对性改进与消融（阶段三）

> 本节结构：**先写机制（现在就能写）**，**结果部分留占位**（等消融与候选集两步走的批次）。
> 消融的预注册见 `EXPERIMENTS.md`（第 15 步节 + D1 节）——**预期必须写在那里，不写在这里**。

## 5.1 判据口径：把 host 侧开销计入预算（对应 §4.4 的"低估"方向）

**问题**（§4.4）：模型只预测前向，而 deadline 约束的是整步 ⇒ 纯 decode 步被**低估**
（b8 漏掉 25.25 ms），造成**错误接纳**。

**改进**：判据改成 `前向预测 + host(该 batch) ≤ 每步预算`。
`host` 是**实测表** + 对表外 batch 的线性拟合（斜率/截距 `(3.705, −4.35)`；
实测三点 (2, 3.06) / (4, 10.76) / (8, 25.29) ms）。

⚠️ **两条边界**：① host **不进模型**（模型不负责 host），进的是判据；
② 它是**本机 + 当前执行路径**的量（含 python 侧打包与 mask 组装），换路径要重测
⇒ 不得写成芯片性质。

⚠️ **一个必须一起报的量**：该改动使"可行候选"大幅减少（因为预算被 host 占掉一部分），
但**"可行候选变少"本身不是收益也不是损失**——控制器有两条降级路径（§6.4 判读纪律 2），
所以必须同时报 D0（可行率）与"实际是否仍在发 prefill"。

**消融**：第 15 步的 `no_host`（去掉该项，其余不变）。
**预期与否证形态**：写在 `EXPERIMENTS.md` 的第 15 步预注册节。

## 5.2 标定协议：秩保证划分 + 覆盖诊断（对应 §4.2）

**问题**（§4.2）：留出误差在划分规则未固定时**没有可比性**；真因是训练集的**秩 / 覆盖不足**。

**改进**：拟合改用 `--split rank_guaranteed`，并把**五个数**（`train n` / `holdout n` /
训练最小秩 / 留出最小秩 / 低估 p95）与**覆盖率**一起报。
**覆盖缺口**用 `scripts/check_model_coverage.py` 在真实轨迹上定位，
按缺口补点（而不是盲目加密网格）。
⚠️ 一条**预注册的止损点**：若秩保证划分下仍 > 5%，说明"按 batch 分段 + 每段线性"这一族的
**上限到此** ⇒ 改走**查表 + 保守回退**，并把**覆盖率**作为头部指标。
该止损点**已被触发**（满秩后仍 6.12%），见 §4.2 与 §8.6。

**消融**：与哈希划分对照（已完成，即 §4.2 的 2×2 解耦）。

## 5.3 标定语义：`uniform` → `real_mixed`（对应 §4.3）

**问题**（§4.3）：标定侧把 `prefill_tok` 当"每条序列各做"，而执行侧是全步总量
⇒ 差约 `batch` 倍，且**不因加密网格自愈**。

**改进**：网格的 `mixed_serving` 组声明 `n_new_mode: real_mixed`
（1 条做全部 + 其余各 1 个），与 harness 的真实结构一致；**新增模型版本，不覆盖旧模型**
（"换模型"是一次新标定，不是对旧模型的修订）。

**自证**：查表键（`_kb()`）**不含** `n_new_mode` ⇒ 光看键分不出两种口径，
因此产物必须显式记录 `shape.n_new_mode`，并由脚本做同键比值核验：
**对照 = `pure_decode` 的同键比值必须 ≈1**（那是守门人），**处理 = `mixed` 的同键比值 ≪1 ≈ 1/batch**。
⚠️ 一个**已发生的失效**必须写进正文（它说明"闸门通过"不等于"跑对了"）：
某批次的链路里，**覆盖率闸门验的是 v6 模型、而配置 `cost_model_path` 指向 v5 模型**
⇒ "用 v6 过闸、用 v5 开跑"，两者指纹相同、加载校验全过、**不报错**。
⇒ 该批**不得**用来声称"语义修复已生效"；该结论登记为**未测**（详见 §1.4 的 P01 待补条）。

## 5.4 候选集：可动范围 vs 评估点（对应 §4.5 假设 1）

**实现事实**（写进正文，因为它影响可复现性）：证据生成侧原先只取
`{chunk_size_min, chunk_size_max}` **两个点** ⇒ **改下限不会自动新增中间点**
（例如把下限降到 128，并不会自动产生 192/256 这两个评估点）。

本项目因此新增 `controller.candidate_chunks`（显式评估点），并把分工写死：

| 配置项 | 含义 |
| --- | --- |
| `chunk_size_min/max` | **可动范围**（运行期上限的唯一权威仍是 `chunk_policy.ChunkLimits`） |
| `candidate_chunks` | **评估点**（控制器在这些点上比较） |

越界**报错**而不静默夹取（夹取会让"改了候选集"这件事**没有发生**，且不报错）。

**两步走的验证**（预注册见 `EXPERIMENTS.md` 的 D1 节）：

① 可行性验证（小候选能否被**预测** / 被**选中** / 被**实际执行**）；
② 单变量对照（`chunk_size_min` ∈ {512, 256, 128}）。

⚠️ ① 里 `chunk_size_min` 与 `candidate_chunks` **一起变**（要让 128 真的可动）⇒
**① 不是单变量实验**，不得用于因果归因；因果只在 ②。
⚠️ **验收标准不是"可行候选比例变高"**，而是：
小 chunk **能被可靠预测 → 能被选中并实际执行 → D1/D2 改善 → 且在公平对照下影响服务指标**。

【待补·P05】① 的可行性结果（来源：`S14G` 的 `cost_pilot` vs `cost_min512`；待跑）。
【待补·P06】② 的下限对照（来源：`S14H` 三点；待跑）。

**`P07` 的前置事实（已测，2026-09-28）**：`P07` 的检验（"遥测中的最小 `prefill_tok`
是否随下限降低而降低"）依赖一个前置事实：**遥测里是否真的记了 `prefill_tok`**。已核：

* 字段**存在**，位于每步 `note` 里，格式
  `prefill_tok=<n> decode=<n> forwards=<n> fwd_ms=<f> pack_ms=<f> readback_ms=<f>`；
* 在 `S14B2-load_ramp-ramp_cost` 的 **3572/3572 步**中逐行出现，**非稀疏**；
* 实测取值样例：`prefill_tok=1024`（首步）/ `512`（后续分块）/ **`0`**（纯 decode 步）
  ⇒ **最小值为 0**，且 0 出现在 decode 步而非"发不出 prefill"。

⇒ `P07` 的检验在**工具层面可行**（读数可得、可解析）。但**本条只是补前置事实**：

【待补·P07】①/② 的机械检验：遥测中出现的**最小** `prefill_tok` 是否随下限降低而降低
（来源：遥测 `note` 的 `prefill_tok=`；**待跑**——现批次只覆盖单一 `chunk_size_min`，
**没有"下限降低"的对照**，不得据现有单批数据先行下结论）。

## 5.5 实现约束与闭环契约

这四条各自对应一个**不会报错**的失效，因此必须显式写出来（也必须在实现里被验证）：

1. **运行期上限只有一处权威**：分块策略读 `chunk_policy.ChunkLimits`，而不是静态配置值 ——
   否则"日志显示调大、实际额度未变"（不抛错、账目也自洽）。
   可核验事实：产物同时记录 `*_requested`（建议）与 `*`（生效），`meta.controller_effect` 汇总差额。
2. **双向可逆**：收缩是防御、放大是恢复；**恢复上限 = 配置初值**（不是参数上界）——
   只有收缩没有恢复的控制器是**棘轮**（负载回落后会把系统永久按在过保守配置上）。
   可核验事实：`n_recovered` / `bottleneck="recover"`。
3. **可行**：`chunk_size ≤ max_batched_tokens`；控制器不得宣告兑现不了的运行点
   （宣告了就会被下游静默夹一次，把第 1 条的检查变成噪声）。
   可核验事实：`n_infeasible_repaired`。
4. **信号要么可信、要么显式为 `None`**：未测信号不参与决策但必须显形
   —— 缓存**关闭**时命中率是 `None`，**不是** `0.0`（"没测" ≠ "测出来没压力"）；
   缓存开着但一次没命中才是 `0.0`。两者对策相反，不可合并。
   可核验事实：`controller_trace[*].signals` 与 `_unavailable_signals`。

⚠️ 一个**静默参数**的历史必须记下来（它是"参数是死的但不报错"的实例）：
冷却字段原名 `cooldown_steps` 并**按推理步**比较，而决策每 `control_interval_steps`（默认 8）步
才发生一次 ⇒ "距上次调整 < 3 步"**永远为假**，冷却从未生效，扫这个参数不会有任何效果。
现在单位改为「观测周期」（`cooldown_cycles`），落到产物里的可核对事实是
`decision_interval_steps`（应恰好等于 `control_interval_steps`）与 `n_skipped_cooldown`。
