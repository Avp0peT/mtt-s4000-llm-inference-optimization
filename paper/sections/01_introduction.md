## 1.1 背景

大语言模型推理服务有两个互相拉扯的目标：**首 token 时延（TTFT）**与**每 token 时延（TPOT）**。
连续批处理把 decode 与 prefill 混在同一步里执行，于是"一步里塞多少 prefill"成了调度器的核心取舍：
塞得多，吞吐高，但正在解码的请求被拉长；塞得少，延迟稳，但吞吐下降。
分块预填充（chunked prefill）就是为这个取舍而生的机制族，而**成本模型驱动的自适应分块**
（成本预测 + next-token deadline + 自适应 chunk）已经把这条路径做成了完整的方法族
（最接近的是 SLOWeave，arXiv:2609.07883）。

本文**不**提出新的调度机制。我们要回答的是一个更前置的问题：

> **当调度器依赖一个"成本模型"来判断"这一步做多少工作还来得及"时，这个判断什么时候会不可靠？
> 不可靠又怎样变成服务代价？**

这个问题之所以值得单独提出来，是因为它在工程上有一个很不友好的性质：**它失效的时候不会报错。**
成本模型给出一个偏乐观的预测，调度器据此接纳一个兑现不了的候选，账目依旧自洽、日志依旧正常，
唯一的变化是请求慢慢变慢——而"慢慢变慢"在端到端指标里与"负载本来就更重"长得一样。

## 1.2 平台与执行特征

平台是 **MTT S4000（MUSA，非 CUDA）** 单卡，模型 `Qwen2.5-7B-Instruct`（fp16），
执行器是本项目自建的**迭代级**执行器（每步一次设备前向批；不使用 vLLM 栈，也不做跨栈比较）。
⚠️ 次平台（昇腾）的配置与产物**不与本平台并表、不互相引用**（`AGENTS.md` 第 3/10 节）。

这带来一个必须写清的前提：**成本画像必须按"执行协议"采，而不是按"快态最小值"采**。
本项目把两者分开（**块 A** = 快态平台：固定形状、连续提交、块尾 sync 一次；
**块 B** = 服务协议：逐步 sync + KV 真实生长），并实测两者差值随 prefill 增大
（b1/pf512：**156.03 ms（A） vs 166.85 ms（B）**）⇒ "只拟合快态最小值"会让预测**系统性偏乐观**
（详见 §3.3）。这两个数取自设备侧探针路径，**不经 harness 盖章、无 `run_id`**
⇒ 按本项目的证据分级它们**不是 `MEASURED`**，因此在本文中只用于**平台特征刻画与性能下界参考**，
**不作**性能结论（`COST_PROFILE_S4000.md` §9 的归因分级表）。

## 1.3 问题陈述

给定**有限的标定数据**与一个**执行状态描述**（我们用来描述"这一步在做什么"的那组特征），
成本预测的可靠性由什么决定？当它失效时，错误怎样传导到调度决策与服务指标？

具体化为三个可检验的子问题：

1. **失效的诊断**：同一个模型、同一份数据的"留出误差"为什么会从 1.77% 变到 95.25%？
   真因是什么？（§4）
2. **失效的两半**：`有限标定数据` 与 `执行状态描述` 这两半各自伤在哪里、性质是否相同？（§4.2 / §4.3）
3. **失效到代价**：预测失配怎样变成**错误接纳**（D1）、**保守等待**（D2）与**达标吞吐**（D3）？（§6）

## 1.4 贡献

**本文不主张**：① 某个新的控制器算法；② 在本平台上优于最接近的方法；③ 跨平台普适或芯片固有机制。
以上三类要么已存在（成本预测 / deadline / 自适应 chunk 均有先作），要么本文证据不足以支撑。

**本文主张**（每条指向已落地的工具与登记行）：

1. **平台与执行特征**（§3）：MTT S4000 上**服务协议**下的逐步成本画像；
   块 A 与块 B **分开采、分开报**，并给出"不能只拟合快态最小值"的实据；
   以及判据侧的实测分解——**模型预测的是前向，而 deadline 约束的是整步**，
   两者相差一笔按序列的 host 开销（b8：130.52 = 104.79 + 25.25 ms）。
2. **成本模型的失效归因**（§4，核心增量）：证明"留出误差"在**划分规则未固定时没有可比性**
   （同一模型 1.77% ↔ 95.25%）；给出**真因是训练集的秩/覆盖不足**、
   **秩保证划分**把同等规模下的误差从 **95.26% 降到 11.77%**，
   以及 **v1 网格在构造上达不到秩 3** 这一必要性论证；
   并用 2×2 解耦把"划分"与"网格"的相对贡献分开（**≈89pp vs ≈5.7pp**）。
3. **执行状态描述的影响**（§4.3）：标定侧与执行侧的同一个字段（每步 prefill token 数）
   **语义不同**（每条序列各做 `prefill_tok` 个新 token vs 全步总量），差约 **`batch` 倍**；
   并说明这一类失效**不会因为加密网格而自愈**——网格再密，只要语义错，每个点都偏同一方向。
   我们给出该口径的判据（产物自证键 `shape.n_new_mode`）与一个应当 ≈1 的守门人对照
   （`pure_decode` 的同键比值）。
   【待补·P01】该语义修的实测验证结论（来源：`S14G` 的 `cost_pilot` vs `cost_min512`；
   当前状态：`S14E` 因配置指向 v5 模型**不构成验证**，故该结论登记为"未测"）。
4. **失配到代价的证据链**（§6）：把 **D0 → D1 → D2 → D3** 做成可复算的链条，
   并给出**适用边界**（哪些负载区能改善、哪些区没有收益）。
   ⚠️ 链条里 **D1 的分母（`d1_n`）必须连报**：本项目实测过 `84.62% → 0.00%` 完全来自分母
   （13 → 2），而不是接纳质量提高。
   ⚠️ 另有一条与"收益"同向但**不同层**的判别纪律：**"候选没被用上" ≠ "用了没用"**
   ——控制器有两条降级路径（无预测 ⇒ 回退阈值控制器；有预测但全超预算 ⇒ 取最省候选），
   实测某批 D0 可行率仅 5.4% 而遥测显示 **183/292 步仍在发 prefill**。

## 1.5 不做什么（scope 边界）

明确排除、**不在正文展开**：前缀缓存、量化、图模式执行、多卡与自定义 kernel。
理由：项目执行依赖里已写明"暂不扩展"，且它们回答的是另外的问题（`paper/experiments.md` §7）。
⇒ 正文里**不**给它们留小节，否则读者会以为它们仍在本研究范围内。

同样明确**不写**的内容：

* 把三处成因（判据口径 / 标定语义 / 候选集）各自的损失占比当成既定结论 ——
  那是**【假设】**，在未用"同模型 / 同 SLO / 同负载"的对照分离出来之前**不得**写成因果；
* 任何"修复后收益"的方向性表述 —— 本文的收益侧证据截至目前**尚未建立**（§7）。
