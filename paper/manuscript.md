# Abstract

> 摘要里**每个量级**都必须能在 §3–§9 找到同一个数字 ⇒ 写完做一次逐句比对。
> `--dry-run`（`TEST_DATA`）产物**不得**出现在摘要里。占位约定见 `paper/WRITING_BRIEF.md` §3。

## 正文（四段）

**问题。** 连续批处理把 decode 与 prefill 混在同一步里执行，"一步塞多少 prefill"由此成为
推理调度器的核心取舍；分块预填充（chunked prefill）正是为这个取舍而生的机制族。
当调度器依赖一个**成本模型**判断"这一步做多少工作还来得及"时，它在**有限标定数据**下
什么时候会不可靠？不可靠又怎样变成服务代价？本文**不**提出新的调度机制，
而是研究这个更前置的问题。

**方法。** 在 MTT S4000（MUSA，非 CUDA）单卡上，用 `Qwen2.5-7B-Instruct`（fp16）与
本项目自建的**迭代级**执行器，把成本模型标定拆成两个可独立检验的维度——
**有限标定数据**（划分规则 / 训练集秩 / 网格覆盖）与**执行状态描述**（同一字段在标定侧与
执行侧的语义是否一致）；判据侧把**逐步按序列的 `host` 开销项**计入每步预算；
并把"预测失配 → 错误决策 → 服务代价"做成可复算的证据链 **D0 → D1 → D2 → D3**
（D0 = 候选被接纳的比例；D1 = 错误接纳；D2 = 保守等待；D3 = 达标吞吐 / 达标率）。
**主指标为 `slo_goodput_tok_s`，并同时报告 `slo_satisfaction_rate` 与 `slo_goodput_req_s`**
（三者不可互相替代）；SLO 在正式比较中冻结为 `ttft_ms = 2000` / `tpot_ms = 100`。

**主要发现（含量级）。**

1. **"留出误差"在划分规则未固定时没有可比性。** 同一个模型、同一份数据，
   仅把划分规则从哈希划分换成秩保证划分，留出低估 p95 从 **95.26% 变成 11.77%**；
   真因是训练集的**秩不足**（该侧训练集里 `batch=8` 只剩纯 decode 点 ⇒ 设计矩阵
   **秩 2 < 参数 3**），不是"划分运气不好"。
2. **扩网格是必要条件，不是调参。** v1 标定网格在构造上**达不到秩 3**（无论怎么划分）；
   2×2 解耦给出两半的相对贡献：**划分规则 ≈ 89pp、网格加密 ≈ 5.7pp**。
   满秩后仍剩 **6.12% > 5%** ⇒ 触发**预注册的止损点**，改走"查表 + 保守回退"。
3. **"补覆盖"不等于"提精度"。** `kv_step = 256` 时查表覆盖率 **53.57%**、保守高估 p95 **0.13%**；
   `kv_step = 1024` 时覆盖率升到 **100%** 而高估 p95 升到 **9.76%**。
   在四臂真机批上同样如此：覆盖率 **53.57% → 100.00%**，而低估 p95 **6.12% → 9.02%**
   ⇒ 两者是**两个独立的量**，不能被同一个"留出误差"数字代表。
4. **口径错的位置不在"模型精度"里。** 真实服务步里存在一笔**按序列**的 host 侧开销
   （实测 b8 一步：整步 **130.52 ms** = 前向 **104.79 ms** + host **25.25 ms**）；
   模型对**前向**是中位 **−4.4%**（准），对**整步**是 **−23.2%**。
   即"模型很准"与"判据偏松"可以同时成立。
5. **一处必须连报分母的量。** 某两批的四臂对照里 D1 从 **84.62% 降到 0.00%**，
   而根因是分母 `d1_n` **13 → 2**，不是接纳质量提高
   ⇒ 只报比率会把"样本变少"读成"变好了"。
   【待补·P28】判据口径与标定语义两项修复各自的净效果（来源：`S14G`/`S14H`/`S14K`；
   当前状态：待跑；⚠️ 必须连报 `d1_n`）。

**结论与边界。** 本文的结论形式是**"预测可靠性由什么决定、失配怎样变成调度代价"**，
而不是"某个控制器更优"：在四臂对照的稳态格上**所有臂的达标吞吐均为 0**
（连静态臂的 TPOT p50 都高于 SLO），该格揭示的是**过载边界**而非性能优势
⇒ 服务收益结论必须由**预注册且 SLO 可达**的负载承担。
【待补·P29】服务收益（`slo_reach` 类负载上的 D3；当前状态：待设计并预注册）。
全部证据来自**单卡 MTT S4000 + 单模型 + 自建迭代级执行器**；
本文**不**声称跨平台普适，**不**把 `host` 这类量归因为芯片固有机制。

# 1 Introduction

> 编号：**阶段制**（唯一权威 `paper/experiments.md` §6）。本节只写散文；
> 事实与登记行的对应关系见 `EXPERIMENTS.md`，方法口径见 `paper/methodology.md`。
> 占位约定见 `paper/WRITING_BRIEF.md` §3。

## 1.1 背景

大语言模型推理服务有两个互相拉扯的目标：**首 token 时延（TTFT）**与**每 token 时延（TPOT）**。
连续批处理把 decode 与 prefill 混在同一步里执行，于是"一步里塞多少 prefill"成了调度器的核心取舍：
塞得多，吞吐高，但正在解码的请求被拉长；塞得少，延迟稳，但吞吐下降。
分块预填充（chunked prefill）就是为这个取舍而生的机制族，而**成本模型驱动的自适应分块**
（成本预测 + next-token deadline + 自适应 chunk）已经把这条路径做成了完整的方法族
（最接近的是 SLOWeave，arXiv:2609.07883）。

本文**不**提出新的调度机制。我们要回答的是一个更前置的问题：

> **当调度器依赖一个"成本模型"来判断"这一步做多少工作还来得及"时，这个判断什么时候会不可靠？
> 不可靠又怎样变成服务代价？**

这个问题之所以值得单独提出来，是因为它在工程上有一个很不友好的性质：**它失效的时候不会报错。**
成本模型给出一个偏乐观的预测，调度器据此接纳一个兑现不了的候选，账目依旧自洽、日志依旧正常，
唯一的变化是请求慢慢变慢——而"慢慢变慢"在端到端指标里与"负载本来就更重"长得一样。

## 1.2 平台与执行特征

平台是 **MTT S4000（MUSA，非 CUDA）** 单卡，模型 `Qwen2.5-7B-Instruct`（fp16），
执行器是本项目自建的**迭代级**执行器（每步一次设备前向批；不使用 vLLM 栈，也不做跨栈比较）。
⚠️ 次平台（昇腾）的配置与产物**不与本平台并表、不互相引用**（`AGENTS.md` 第 3/10 节）。

这带来一个必须写清的前提：**成本画像必须按"执行协议"采，而不是按"快态最小值"采**。
本项目把两者分开（**块 A** = 快态平台：固定形状、连续提交、块尾 sync 一次；
**块 B** = 服务协议：逐步 sync + KV 真实生长），并实测两者差值随 prefill 增大
（b1/pf512：**156.03 ms（A） vs 166.85 ms（B）**）⇒ "只拟合快态最小值"会让预测**系统性偏乐观**
（详见 §3.3）。这两个数取自设备侧探针路径，**不经 harness 盖章、无 `run_id`**
⇒ 按本项目的证据分级它们**不是 `MEASURED`**，因此在本文中只用于**平台特征刻画与性能下界参考**，
**不作**性能结论（`COST_PROFILE_S4000.md` §9 的归因分级表）。

## 1.3 问题陈述

给定**有限的标定数据**与一个**执行状态描述**（我们用来描述"这一步在做什么"的那组特征），
成本预测的可靠性由什么决定？当它失效时，错误怎样传导到调度决策与服务指标？

具体化为三个可检验的子问题：

1. **失效的诊断**：同一个模型、同一份数据的"留出误差"为什么会从 1.77% 变到 95.25%？
   真因是什么？（§4）
2. **失效的两半**：`有限标定数据` 与 `执行状态描述` 这两半各自伤在哪里、性质是否相同？（§4.2 / §4.3）
3. **失效到代价**：预测失配怎样变成**错误接纳**（D1）、**保守等待**（D2）与**达标吞吐**（D3）？（§6）

## 1.4 贡献

**本文不主张**：① 某个新的控制器算法；② 在本平台上优于最接近的方法；③ 跨平台普适或芯片固有机制。
以上三类要么已存在（成本预测 / deadline / 自适应 chunk 均有先作），要么本文证据不足以支撑。

**本文主张**（每条指向已落地的工具与登记行）：

1. **平台与执行特征**（§3）：MTT S4000 上**服务协议**下的逐步成本画像；
   块 A 与块 B **分开采、分开报**，并给出"不能只拟合快态最小值"的实据；
   以及判据侧的实测分解——**模型预测的是前向，而 deadline 约束的是整步**，
   两者相差一笔按序列的 host 开销（b8：130.52 = 104.79 + 25.25 ms）。
2. **成本模型的失效归因**（§4，核心增量）：证明"留出误差"在**划分规则未固定时没有可比性**
   （同一模型 1.77% ↔ 95.25%）；给出**真因是训练集的秩/覆盖不足**、
   **秩保证划分**把同等规模下的误差从 **95.26% 降到 11.77%**，
   以及 **v1 网格在构造上达不到秩 3** 这一必要性论证；
   并用 2×2 解耦把"划分"与"网格"的相对贡献分开（**≈89pp vs ≈5.7pp**）。
3. **执行状态描述的影响**（§4.3）：标定侧与执行侧的同一个字段（每步 prefill token 数）
   **语义不同**（每条序列各做 `prefill_tok` 个新 token vs 全步总量），差约 **`batch` 倍**；
   并说明这一类失效**不会因为加密网格而自愈**——网格再密，只要语义错，每个点都偏同一方向。
   我们给出该口径的判据（产物自证键 `shape.n_new_mode`）与一个应当 ≈1 的守门人对照
   （`pure_decode` 的同键比值）。
   【待补·P01】该语义修的实测验证结论（来源：`S14G` 的 `cost_pilot` vs `cost_min512`；
   当前状态：`S14E` 因配置指向 v5 模型**不构成验证**，故该结论登记为"未测"）。
4. **失配到代价的证据链**（§6）：把 **D0 → D1 → D2 → D3** 做成可复算的链条，
   并给出**适用边界**（哪些负载区能改善、哪些区没有收益）。
   ⚠️ 链条里 **D1 的分母（`d1_n`）必须连报**：本项目实测过 `84.62% → 0.00%` 完全来自分母
   （13 → 2），而不是接纳质量提高。
   ⚠️ 另有一条与"收益"同向但**不同层**的判别纪律：**"候选没被用上" ≠ "用了没用"**
   ——控制器有两条降级路径（无预测 ⇒ 回退阈值控制器；有预测但全超预算 ⇒ 取最省候选），
   实测某批 D0 可行率仅 5.4% 而遥测显示 **183/292 步仍在发 prefill**。

# 2 Background & Related Work

> 引用纪律：**只引 `SOURCES.md` 里状态为 `verified` 的条目**；`unverified` 的一律不引。
> 在相关工作评审支持之前，**不得**声称本文贡献具有新颖性（`AGENTS.md` 第 16/17 节）。

## 2.1 推理两阶段与各自瓶颈

自回归推理分 prefill（一次前向吃下整段 prompt，产出 KV）与 decode（每步 1 token）。
两者的资源特征不同：prefill 偏算力、decode 偏带宽与 KV 访问。
在同一张卡上把两者混步执行，就产生了"这一步给 prefill 多少 token"的取舍 ——
这正是本文所有调度决策的**被控量**。

本项目在该平台上实测到的执行特征（§3）有两条直接影响建模：
① 一步的成本是**分组加和**的（`real_backend` 按每个序列新增 token 数分组串行前向），
batch 是**次线性**主项（b1 59.9 → b8 109.2 ms，**1.82×**）；
② 一步里除前向之外还有一笔**按序列**的 host 侧开销（打包 / mask 组装 / 取回），
b8 时约 **25 ms**，与"每步预算"同量级 —— 而模型只预测前向。

## 2.2 分块预填充与调度（本文的对照对象）

* **Sarathi-Serve**（OSDI '24）提出分块预填充 + stall-free 调度，是本文**固定分块静态基线**
  的直接来源。本文的静态臂即按它的思路取"固定 chunk / 固定单步 token 预算"。
  ⚠️ 其开源实现自述为**研究原型**（vLLM fork，功能不完整）⇒ 本文只借用其**调度规则**，
  不声称"复现了完整系统"。
* **DistServe**（OSDI '24）给出 **goodput** 的定义与讨论口径，并量化 prefill-decode 干扰；
  其**多设备分离**架构不在本文范围内，但 goodput 的口径被本文沿用
  （`paper/methodology.md` §1；本文进一步把它拆成三个不可互相替代的数）。

## 2.3 自适应分块与成本预测（最接近的一族）

* **SLOWeave**（arXiv:2609.07883）—— **与本文第三臂最接近**：成本预测 + next-token deadline +
  自适应 chunk。其方法选择"预测能在最早活跃 decode 的 next-token deadline 前完成的
  **最大** prefill chunk"，对**单调迭代成本模型**做**对数时间搜索**，且**无需按负载调** chunk size；
  作者强调方法**刻意收窄**（不改编排路径、不改 kernel）。
  评测为 event-driven 模拟器 + iteration-level GPU runtime，四类负载（chat / mixed / long / **bursty**），
  TPOT 目标 10/25/50 ms、TTFT SLO 1000/1500/5000 ms；25 ms 目标下 goodput 比最强固定 chunk 基线
  **+39%（mixed）/ +38%（long）**，10 ms 目标下升至 **3.3× / 2.4×**。
  本项目实现了它的算法作为**对照臂**（`src/ascend_opt/slo_weave.py`），
  因此本文**不**把"成本模型 + deadline + 自适应 chunk"当作算法贡献。
  ⚠️ 两点必须并记：① 它的 artifact 在论文中**声明存在**，但本轮检索**未找到可访问仓库**
  ⇒ 我们的实现属"按论文写的 policy 参考版本"，**不得**冒称完整复现；
  ② 作者自述局限——真实迭代成本**可能非平滑**（kernel 边界、张量并行通信、显存压力、前缀命中）
  ⇒ **标定漂移**需要更广泛部署研究；**持续过载时严格 TPOT 目标可能没有安全的 prefill 预算**。
* **DRLServe**（ECAI 2025）代表**学习型**路线（RAPC / TAPPO，把推理建模为 MDP）。
  本文不做强化学习，但把它列为"同族的另一条路"，用以说明"自适应 chunk"这一族已有多条实现路径。

## 2.4 与本文的差异

既有的这一族工作，评价重点在"**机制是否有效**"（吞吐/延迟改进了多少）。
本文把重心前移一格：**在机制给定的前提下，预测可靠性由什么决定**。
具体差异：

1. 我们报告"**留出误差在划分规则未固定时没有可比性**"这一现象，并给出真因（秩 / 覆盖不足）
   —— 这是**评估协议**层面的事，与机制无关；
2. 我们区分失效的**两半**（有限标定数据 / 执行状态描述），并指出后者**不会因加密标定网格而自愈**；
3. 我们用 **D0/D1/D2/D3** 把"预测失配"接到"服务代价"，而不是只看端到端指标
   —— 因为端到端指标会把"没被用上"与"用了没用"混在一起；

## 3.2 模型与执行形状

被调度的"一步"可以用三个量加一个计数描述：`batch`（正在解码的序列数）、
`prefill_tok`（这一步新吃进的 prefill token 数）、`kv_len`（上下文长度）、
`n_forwards`（本步串行前向数）。**真实服务步的形状分布**由 `scripts/check_model_coverage.py`
在真实轨迹上普查得到 —— 它同时是"标定网格该往哪里补"的依据（§4.2 的覆盖问题由此提出）。

被测负载之一的形状（`short_chat` 族）：求入长度 1536、并发 16；另一族为
`phase1_anchor`（prompt 恒 2048、gen 128）。⚠️ `chunk_size = 2048` 在该负载上
**等于整段 prompt** ⇒ "分块"是**恒等操作**，与"不分块"**构造性等价**（§6 的响应面由此只有 4 个
不同配置，而不是 5 个）。

⚠️ **字段口径**：执行侧记录的 `prefill_tok` 是**全步总量**（一步内所有序列新增的 prefill token 之和），
而"每条序列各做多少"是另一个量。这两者的混淆是 §4.3 的主题，**本节只登记字段定义**。

## 3.3 块 A 与块 B：不能只拟合快态最小值

* **块 A（快态平台）**：固定形状、连续提交（async 块：连续提交 N 次、块尾 sync 一次 ⇒ 占空比 ≈100%），
  取**块最小值**，测的是稳态吞吐**下界**；
* **块 B（服务协议）**：逐步 `sync` + KV 真实生长，即真实服务路径。

实测两者差值随 prefill 增大：**b1/pf512 时 156.03 ms（A） vs 166.85 ms（B）**。
⇒ 结论（事实）：**块 A 只能作为性能下界参考**，用它拟合 SLO 预测会**系统性偏乐观**。

⚠️ **这两数不是 `MEASURED`**（设备侧探针、无 `run_id`、不盖标签）⇒ 只作平台特征，
不进性能结论表。此外有一条**长期有效的标定纪律**：**形状比值可信（会话内 ±0.3%）、
绝对值跨会话漂移 1.3–4%** ⇒ 成本模型只能用**同会话内**对照，不得跨会话并表。

设备还有**多档性能态**（b1 快 ~57–60 ms / 慢 ~76–82 ms，在几秒尺度双向翻转），
**占空比是开关**；它直接决定"怎么测"。因此本项目的可信标定协议固定为
**async 块 + warmup + 取块最小值**。
⚠️ **有限观察**（不是"已排除全部原因"）：采样时刻看不到 DVFS（gfx clock 恒 1660 MHz）、
热节流（恒 42 °C）、进程争抢（无其他 GPU 进程）—— 这不等于这些机制不存在，
尤其 `clock 的 min == max` 可能本身就是被限频策略钉住的**结果**。

## 3.4 分层信号：为什么裸 TPOT 会被 prefill 污染

调度器要读一个"延迟信号"来决定动作。若直接读**每步的 TPOT**，那么"这一步做了 prefill"
会让该步对应的 token 间隔被拉长，于是读数反映的是**这一步干了多少活**，而不是"服务是否在变慢"。

**实测（登记行 E10，`P8FULL`，`load_ramp`，3 轮）**：一次观测窗内，控制器读到的
`tpot_p90` 是 **337.2 / 337.9 / 342.2 ms**，而同一窗口里**纯 decode 步**的 `fwd_ms` p50 只有
**61.4 / 61.6 / 62.5 ms（n=28）**、**含 prefill 的步** p50 为 **329.3 / 329.0 / 331.5 ms（n=4）**
⇒ **读数 ≈ 真实 decode 的 5.5 倍，且几乎全部来自那 4 个 prefill 步**。

⚠️ 后果**不只是"读数错"**：这 9 次动作**全部是收缩**（把 `max_batched_tokens` 从 8192 压到
下界 2048），**纯 decode 步的 `fwd_ms` p50 随之从 61/62/62 ms 升到 118/118/118 ms（≈ +92%）**
—— 动作本身把真实的 decode 延迟弄慢了近一倍，而它要修的"问题"（337 ms）在纯 decode 口径下
并不存在。**触发时 `queue_depth` 三个 run 都是 0**（即**没有人排队时收缩**）。

⇒ 本项目的判据因此**冻结为 `decode_p90`**（只统计纯 decode 步），并把
`signal_mode: layered` 写进配置与产物（`describe()` 记录 `signal_mode` / `signal_criterion`）。

⚠️ 这条冻结不是"更好的读数"的口味问题：它是**判据的可比性前提** ——
换读数会改变调度（改门限 / 改判据都会改调度 ⇒ 必须重跑）。
⚠️ 同时注意：**用户真实经历的 prefill 停顿必须继续进入 ITL / TPOT / stall / SLO**，
不得用"纯 decode"美化对外指标。分层是**内部诊断量**，不是对外指标。

**该改动的干预实验（登记行 E12，单变量 `signal_criterion`，2 臂 × 3 轮）**：
换判据后**报告值 ÷ 同窗纯 decode** 从 **5.47 / 5.47 / 5.73** 降到 **1.33 / 1.33 / 1.32**
（即报告的就是纯 decode 值），且"在纯 decode 还只有 61 ms 时收缩"的动作消失
（首次动作由 `t ≈ 123.0 s` 推迟到 **`t ≈ 131.2 s`**，且触发值 138.0 **> 门限 129.6**
⇒ 属**合法触发**：8 槽满批时纯 decode 真的变慢）。
但**净收益很小、且代价是 stall**：达标率 **0.1957 → 0.2065**（**18 → 19 个请求**）；
`tpot` p50 **182.53 → 180.79**；**`stall` p99 330.51 → 410.30（回到 static 的 412.4 水平）**。
⇒ 机制成立，但这是**权衡**，不是"换判据就更好"。

## 3.5 判据的组成部分：整步 ≠ 前向

调度器比的是"这一步还来不来得及"，而**模型只预测前向**。

**实测（登记行 S14B1，`scripts/decompose_step_overhead.py` 的 65 组配对）**：
**整步 130.52 ms = 前向 104.79 ms + host 25.25 ms**（`pack_ms` 24.94 + `readback_ms` 0.31）。
模型对**前向**是中位 **−4.4%**（准），对**整步**是 **−23.2%**。

⇒ 判据必须写成 `预测整步 = 前向预测 + host(该 batch)`，其中 host 是**本机 + 当前执行路径**的量
（含 python 侧打包 / mask 组装），**不是**芯片性质 ⇒ 换执行路径或改 batch 上限**必须重测**。

⚠️ **判据口径的三项必须进产物**（`host_overhead_ms` / `host_overhead_fit` / `apply_safety_margin`），
否则事后无法区分"这次跑的是哪种口径"。本项目实测踩过：两批产物的 `config.controller`
在这一点上**完全相同**，只能靠配置 + `git_commit` 反推。
【待补·P04】该修复后的产物自证示例（来源：`S14G` 起的批次；当前状态：修复已落地，批次待跑）。

⚠️ **一条与"改判据"同源的纪律**：`host` 项**不进模型**（模型不负责 host），
进的是**判据**；且它与"模型精度"是两件事——**"模型很准"与"判据偏松"可以同时成立**
（−4.4% vs −23.2% 就是同一次测量里的两个数）。

## 3.6 复现性与数据完整性

## 4.2 「有限标定数据」这一半

**【事实 2】真因是训练集的秩不足，不是"划分运气不好"。**

**在这一步之前，判据本身不可信**（它测的是秩亏）。

**【事实 6】2×2 解耦（留出 43 点 ⇒ 判据可信）**：
划分规则贡献 ≈ **89pp**、网格加密 ≈ **5.7pp**；秩保证划分下 v4 仍 **6.12% > 5%**
⇒ 触发**预注册的止损点**，转"查表 + 保守回退"。证据：`decouple_v3_v4.json`。

⇒ **一眼可见：哈希列两代几乎不动（95.25% → 95.26%），秩保证列随网格加密下降

**不得**据 `kv_step=0` 的低 `over_p95` 说它最好。

> **【解释】** "有限标定数据"伤的不是"点不够密"，而是**形状空间的覆盖**：
> ① 训练集的**秩**决定模型在那一段能不能被**辨识**（事实 2/3）；
> ② 网格的**覆盖**决定部署时**有没有键**（事实 7）。
> 这两件事都**不会因为"多跑几次同样的点"而改善**，也不会出现在"留出误差"那一个数字里。
> ⚠️ 这是解释，不是测量 —— 要证它，需要"同一模型下分别改变秩与覆盖"的对照（事实 6 就是其中一次）。

## 4.3 「执行状态描述」这一半

**【事实 8】标定的 `prefill_tok` 与 harness 的 `tokens_prefilled` **语义不同**：**
标定探针把它当**每条序列各做** `prefill_tok` 个新 token；harness 记的是**全步总量**。
⇒ 同一列在两边的含义差约 **`batch` 倍**。
证据（逐字）：探针 `scripts/fwd_costcalib_probe.py` 的 `make_batch` +
遥测 `note` 里 `prefill_tok=512 decode=7`（7 条在解码 + 1 条分到 512 个 prefill token）。

**【事实 9】该口径错在真机数据上可见。**
`S14D` 的 `fixed_cost` 里出现 `预测 943.1 + host 21.6 = 964.7ms 超每步预算 120.0ms`、
`预测 1042.9 + host 25.3 = 1068.2ms …` 这类拒绝；而同一 run 里另一类拒绝是
`预测 108.6 + host 25.3 = 133.9ms`。**两类量级差约一个数量级**。
证据：`results/raw/S14D-short_chat-fixed_cost/meta.json` 的 `controller_trace`。

**【事实 10】v6 把该口径改成 `real_mixed`（1 条做全部 + 其余各 1 个），并写入网格。**
证据：`configs/cost_calib/shape_grid_v6.yaml` 的 `mixed_serving` 组 `n_new_mode: real_mixed`；
产物自证靠 `shape.n_new_mode`（键 `_kb()` **不含**该字段 ⇒ 光看键分不出两种口径）。

> **【解释】** 这一类失效与 4.2 **性质不同**：它**不会因为加密网格而自愈**
> —— 网格再密，只要语义错，每个点的预测都偏同一方向。
> ⚠️ 解释，不是测量。**v6 是否真的修好了，到本文档撰写时仍未验证**（见 4.5 【假设 2】）。

## 4.4 两个方向相反的系统误差（这才是完整图景）

**【事实 11】host 侧开销实测（b8 的一步）**：
整步 **130.52 ms** = 前向 **104.79** + host **25.25**（`pack_ms` 24.94 + `readback_ms` 0.31）。
而模型对**前向**是中位 **−4.4%**（准），对**整步**是 **−23.2%**。
证据：`scripts/decompose_step_overhead.py`（配对 65 组）、`results/processed/step_overhead.json`。

| 步的类型 | 误差方向 | 机制 | 后果 |
| --- | --- | --- | --- |
| **纯 decode 步** | **低估** | 模型只预测**前向**，而预算比的是**整步** ⇒ 漏掉 host（b8 ≈ 25 ms） | 错误接纳 ⇒ **D1** |
| **prefill 重的步** | **高估 ~b 倍** | 4.3 的语义错 | 大量候选被判不可行 |

**【事实 12】判据口径此前**未进产物**：`describe()` 原先不记 `host_overhead_ms` /
`host_overhead_fit` / `apply_safety_margin` ⇒ `S14B1`（无 host 项）与 `S14D`（有 host 项）
的 `config.controller` 在这一点上**完全相同**。
⇒ 现在已补（`e814e2a`）。⚠️ 但对**已入库**的批次，这三项**数不出来**，只能靠配置 + `git_commit` 反推。

**【事实 13】"候选不可行"不等于"不动作"。**
`cost_policy.py` 有两条降级路径：`predicted` 为空 ⇒ `_fallback()` **回退到阈值控制器**
（照常发 prefill）；有预测但全超预算 ⇒ **取最省那个**（`n_degraded`）。
实测（`S14B1` `fixed_cost`）：遥测 `note` 里 **183/292 步实际发了 prefill**
（step0–2 = `prefill_tok=1024 fwd_ms=251.69`），而同一 run 有 **145 个候选"模型范围外"**。
旁证：该 run 的 cost 与 threshold 臂 **D2（26.71% / Σ队列 624）与 TTFT（8321 vs 8320）
几乎逐位相同** —— 回退之后就是同一个控制器。

**【事实 14】D0（候选被接纳的比例）在真机上的量级。**
`S14D` `fixed_cost`：**37 次决策 / ~141 次候选评估 / 仅 8 个可行 = 5.7%**；
`S14B1` `fixed_cost`：**185 / 280 / 95 = 33.9%**，拒因 `145× 模型范围外` + `40× 预测 998.3ms 超预算`。
⇒ 两批的**可行率与拒因性质都不同**（前者以"判据超预算"为主，后者以"模型范围外"为主）。

> **【解释】** 事实 11 的两个误差**符号相反、成因不同**，而且**都不在"模型精度"那一个数字里**
> —— 第 11 步报的"低估 p95 1.77%"只测**标定集内部**的插值误差，**测不到跨口径的错**。
> ⚠️ 解释。要分离它们各自的贡献，需要**同模型/同 SLO/同负载**的对照，**尚未跑**（见 4.5【假设 3】）。

## 5.1 判据口径：把 host 侧开销计入预算（对应 §4.4 的"低估"方向）

**问题**（§4.4）：模型只预测前向，而 deadline 约束的是整步 ⇒ 纯 decode 步被**低估**
（b8 漏掉 25.25 ms），造成**错误接纳**。

**改进**：判据改成 `前向预测 + host(该 batch) ≤ 每步预算`。
`host` 是**实测表** + 对表外 batch 的线性拟合（斜率/截距 `(3.705, −4.35)`；
实测三点 (2, 3.06) / (4, 10.76) / (8, 25.29) ms）。

⚠️ **两条边界**：① host **不进模型**（模型不负责 host），进的是判据；
② 它是**本机 + 当前执行路径**的量（含 python 侧打包与 mask 组装），换路径要重测
⇒ 不得写成芯片性质。

⚠️ **一个必须一起报的量**：该改动使"可行候选"大幅减少（因为预算被 host 占掉一部分），
但**"可行候选变少"本身不是收益也不是损失**——控制器有两条降级路径（§6.4 判读纪律 2），
所以必须同时报 D0（可行率）与"实际是否仍在发 prefill"。

**消融**：第 15 步的 `no_host`（去掉该项，其余不变）。
**预期与否证形态**：写在 `EXPERIMENTS.md` 的第 15 步预注册节。

## 5.2 标定协议：秩保证划分 + 覆盖诊断（对应 §4.2）

**问题**（§4.2）：留出误差在划分规则未固定时**没有可比性**；真因是训练集的**秩 / 覆盖不足**。

**改进**：拟合改用 `--split rank_guaranteed`，并把**五个数**（`train n` / `holdout n` /
训练最小秩 / 留出最小秩 / 低估 p95）与**覆盖率**一起报。
**覆盖缺口**用 `scripts/check_model_coverage.py` 在真实轨迹上定位，
按缺口补点（而不是盲目加密网格）。
⚠️ 一条**预注册的止损点**：若秩保证划分下仍 > 5%，说明"按 batch 分段 + 每段线性"这一族的
**上限到此** ⇒ 改走**查表 + 保守回退**，并把**覆盖率**作为头部指标。
该止损点**已被触发**（满秩后仍 6.12%），见 §4.2 与 §8.6。

**消融**：与哈希划分对照（已完成，即 §4.2 的 2×2 解耦）。

## 5.3 标定语义：`uniform` → `real_mixed`（对应 §4.3）

**问题**（§4.3）：标定侧把 `prefill_tok` 当"每条序列各做"，而执行侧是全步总量
⇒ 差约 `batch` 倍，且**不因加密网格自愈**。

**改进**：网格的 `mixed_serving` 组声明 `n_new_mode: real_mixed`
（1 条做全部 + 其余各 1 个），与 harness 的真实结构一致；**新增模型版本，不覆盖旧模型**
（"换模型"是一次新标定，不是对旧模型的修订）。

**自证**：查表键（`_kb()`）**不含** `n_new_mode` ⇒ 光看键分不出两种口径，
因此产物必须显式记录 `shape.n_new_mode`，并由脚本做同键比值核验：
**对照 = `pure_decode` 的同键比值必须 ≈1**（那是守门人），**处理 = `mixed` 的同键比值 ≪1 ≈ 1/batch**。
⚠️ 一个**已发生的失效**必须写进正文（它说明"闸门通过"不等于"跑对了"）：
某批次的链路里，**覆盖率闸门验的是 v6 模型、而配置 `cost_model_path` 指向 v5 模型**
⇒ "用 v6 过闸、用 v5 开跑"，两者指纹相同、加载校验全过、**不报错**。
⇒ 该批**不得**用来声称"语义修复已生效"；该结论登记为**未测**（详见 §1.4 的 P01 待补条）。

## 5.4 候选集：可动范围 vs 评估点（对应 §4.5 假设 1）

**实现事实**（写进正文，因为它影响可复现性）：证据生成侧原先只取
`{chunk_size_min, chunk_size_max}` **两个点** ⇒ **改下限不会自动新增中间点**
（例如把下限降到 128，并不会自动产生 192/256 这两个评估点）。

本项目因此新增 `controller.candidate_chunks`（显式评估点），并把分工写死：

| 配置项 | 含义 |
| --- | --- |
| `chunk_size_min/max` | **可动范围**（运行期上限的唯一权威仍是 `chunk_policy.ChunkLimits`） |
| `candidate_chunks` | **评估点**（控制器在这些点上比较） |

越界**报错**而不静默夹取（夹取会让"改了候选集"这件事**没有发生**，且不报错）。

**两步走的验证**（预注册见 `EXPERIMENTS.md` 的 D1 节）：

① 可行性验证（小候选能否被**预测** / 被**选中** / 被**实际执行**）；
② 单变量对照（`chunk_size_min` ∈ {512, 256, 128}）。

⚠️ ① 里 `chunk_size_min` 与 `candidate_chunks` **一起变**（要让 128 真的可动）⇒
**① 不是单变量实验**，不得用于因果归因；因果只在 ②。
⚠️ **验收标准不是"可行候选比例变高"**，而是：
小 chunk **能被可靠预测 → 能被选中并实际执行 → D1/D2 改善 → 且在公平对照下影响服务指标**。

【待补·P05】① 的可行性结果（来源：`S14G` 的 `cost_pilot` vs `cost_min512`；待跑）。
【待补·P06】② 的下限对照（来源：`S14H` 三点；待跑）。

**`P07` 的前置事实（已测，2026-09-28）**：`P07` 的检验（"遥测中的最小 `prefill_tok`
是否随下限降低而降低"）依赖一个前置事实：**遥测里是否真的记了 `prefill_tok`**。已核：

* 字段**存在**，位于每步 `note` 里，格式
  `prefill_tok=<n> decode=<n> forwards=<n> fwd_ms=<f> pack_ms=<f> readback_ms=<f>`；
* 在 `S14B2-load_ramp-ramp_cost` 的 **3572/3572 步**中逐行出现，**非稀疏**；
* 实测取值样例：`prefill_tok=1024`（首步）/ `512`（后续分块）/ **`0`**（纯 decode 步）
  ⇒ **最小值为 0**，且 0 出现在 decode 步而非"发不出 prefill"。

⇒ `P07` 的检验在**工具层面可行**（读数可得、可解析）。但**本条只是补前置事实**：

【待补·P07】①/② 的机械检验：遥测中出现的**最小** `prefill_tok` 是否随下限降低而降低
（来源：遥测 `note` 的 `prefill_tok=`；**待跑**——现批次只覆盖单一 `chunk_size_min`，
**没有"下限降低"的对照**，不得据现有单批数据先行下结论）。

## 5.5 实现约束与闭环契约

这四条各自对应一个**不会报错**的失效，因此必须显式写出来（也必须在实现里被验证）：

1. **运行期上限只有一处权威**：分块策略读 `chunk_policy.ChunkLimits`，而不是静态配置值 ——
   否则"日志显示调大、实际额度未变"（不抛错、账目也自洽）。
   可核验事实：产物同时记录 `*_requested`（建议）与 `*`（生效），`meta.controller_effect` 汇总差额。
2. **双向可逆**：收缩是防御、放大是恢复；**恢复上限 = 配置初值**（不是参数上界）——
   只有收缩没有恢复的控制器是**棘轮**（负载回落后会把系统永久按在过保守配置上）。
   可核验事实：`n_recovered` / `bottleneck="recover"`。
3. **可行**：`chunk_size ≤ max_batched_tokens`；控制器不得宣告兑现不了的运行点
   （宣告了就会被下游静默夹一次，把第 1 条的检查变成噪声）。
   可核验事实：`n_infeasible_repaired`。
4. **信号要么可信、要么显式为 `None`**：未测信号不参与决策但必须显形
   —— 缓存**关闭**时命中率是 `None`，**不是** `0.0`（"没测" ≠ "测出来没压力"）；
   缓存开着但一次没命中才是 `0.0`。两者对策相反，不可合并。
   可核验事实：`controller_trace[*].signals` 与 `_unavailable_signals`。

⚠️ 一个**静默参数**的历史必须记下来（它是"参数是死的但不报错"的实例）：
冷却字段原名 `cooldown_steps` 并**按推理步**比较，而决策每 `control_interval_steps`（默认 8）步
才发生一次 ⇒ "距上次调整 < 3 步"**永远为假**，冷却从未生效，扫这个参数不会有任何效果。
现在单位改为「观测周期」（`cooldown_cycles`），落到产物里的可核对事实是
`decision_interval_steps`（应恰好等于 `control_interval_steps`）与 `n_skipped_cooldown`。

## 6.1 负载与 cell

| cell | 代表什么真实场景 | 为什么需要它 | 现状 |
| --- | --- | --- | --- |
| `fixed` | 稳态服务（固定长度、固定并发） | **检查用**（形状固定，便于横向比较各臂） | ✅ 已跑（`S14B1`，四臂 × 5 重复） |
| `ramp` | 非平稳负载（low → high → recover，`piecewise` λ(t)） | 与最接近方法（SLOWeave 评的是到达分布）的**真正差异点** | 🟡 部分跑（`P8FULL` / `S9AB` / `S10`） |
| `lenmix` | 请求长度分布变化 | 长短混合下的取舍 | ⬜ 未跑 |
| `slo_reach` | 更轻、**SLO 可达**的格 | 让"达标吞吐"这个头条量**有区分度** | ⬜ 待登记（需提前冻结设计并说明原因） |

⚠️ **`fixed` 格上四臂达标吞吐全为 0**（连 `static` 的 TPOT p50 = 156.0 ms 都高于 SLO 100 ms）⇒
该格揭示的是**过载边界**，**不能**用来证明一般性能优势。
⇒ 服务收益的结论**必须**由 `slo_reach` 这类**预注册且 SLO 可达**的负载承担。

## 6.2 指标口径

* 尾延迟：**TPOT 与 TPOT stall 分开报**。理由：均值会被大量快请求"平均"掉 ——
  实测同一 run 内 TPOT 均值的 P99 = 74 ms，而单请求 token 间隔的 **P50 = 968 ms**，
  **差一个数量级**（链路口径核对时的 dry-run 观测）。
* 吞吐：tok/s；**窗口长度**用测量段墙钟，不用"最后完成时刻"（后者会把排空尾段从分母里抹掉）。
* SLO：`tpot_ms = 100`、`ttft_ms = 2000`。
  标定依据：逐请求 TPOT 实测区间 **[61.7, 168.0] ms**（原阈值 50 **低于下界** ⇒ 恒不可达
  ⇒ 达标率三列恒 0，属"判据无效"而非"达标率低"）。
  阈值 90 / 100 / 110 的**定性分档完全相同**（c1/c2 通过、c4 按臂分裂、c8 全失败）
  ⇒ 结论对该选择**稳健**，差异只在 c4 的粒度（90 全否 / 100 给 1/8 / 110 给 4/8）；
  选 100 的理由是它同时等于 **10 tok/s** 这一外部可辩护的交互式边界。
  ⚠️ 该阈值对 `chunk_size` 敏感是**有意为之**（c4 的"不分块 88.7 / 分块 110.4"分列阈值两侧），
  代价是标定与本负载/本 chunk 取值绑定，换负载或换 chunk 档位**必须重采**。
* 控制门限：`target_tpot_ms = 120`、`hysteresis = 0.08` ⇒ 放大 **110.4** / 收缩 **129.6** ms。
  标定依据：旧门限 110×0.9 = **99.0 落在 c4 实测工作点 97.8–99.2 内部**，
  余量只剩 0.0112 ⇒ 同一份配置三次重复的 TTFT 出现 `481.4 / 481.6 / 652.1`（**+43%**）。
  ⚠️ **改门限会改调度 ⇒ 必须重跑**；门限变了就不能与旧批并表。
  ⚠️ **结构性障碍未解除**：工作点 `tpot_p90` 跨 **61.8 → 571.7 ms（9.3×）**，
  而滞回带宽度是固定绝对值 `2h·target` ≈ **19.2 ms** ⇒ 绝对阈值 + 单一 `(target, h)`
  无法与多档工作点分开。理由要说**负载扫描**（负载连续变化会扫过整条区间 ⇒ 必然有档位落在带内）。

## 6.3 重复、预热与离散度

* 每格 **≥3 次重复**；以**独立运行**为统计单位。
* 预热在计时窗口**之外**（默认 ≥30 s，按时间而非固定迭代数）；离散度用
  **稳健 CV = 1.4826·MAD / 中位数**（普通 CV 会被单个 outlier 毁掉）。
* 噪声底必须先于结论引用（`P1S3D`，12 格 × 3 重复的稳健 CV）：
  `TTFT p50` 中位 **0.0002** / 最大 **0.0007**；`TPOT p50` 中位 **0.0004** / 最大 **0.0024**；
  `stall p99` 中位 **0.0009** / 最大 **0.0341**。
  ⚠️ `stall p99` 的最大值被**单一格**抬高（`static_c8` 三轮 `498.28 / 464.59 / 464.22`，
  稳健 CV 0.0012 而普通 CV **0.0411**，单点离群被 MAD 抹平）⇒ 引用该批的 `stall p99`
  噪声底**必须用 3.41%**，用其余 11 格的中位 0.09% 会把该离群藏掉。
* ⚠️ **`ramp` 的稳定性必须按段判**：整段 CV 反映的是**负载形状**而不是测量噪声
  （实测 `S10` 的整段 CV 高达 **1.44**）。同理**不得**用整段汇总的达标吞吐去复核冻结决定。
* ⚠️ **`spread = 0` 不等于"这台机器没有噪声"**：开放环确定性的 `ramp` 上，同一格 3 次重复
  在段级达标吞吐上**逐位相同**（如 high 段 `1.422222 ×3`）——那是**进程内、段级派生量**的极差。

## 6.4 证据链：D0 → D1 → D2 → D3

| 量 | 定义 | 它回答的问题 |
| --- | --- | --- |
| **D0** | **候选被接纳的比例** + 拒因分组 | 控制器**有没有被用上**？ |
| **D1** | 选中可行候选后，**下一步实际时长 > deadline** 的比例 | 有没有**错误接纳** |
| **D2** | `prefill 额度 = 0 且队列非空`的步占比 + `Σ队列·步` | 有没有让人**干等** |
| **D3** | 达标吞吐 / 达标率 | 最终**服务收益**（为 0 也要照报并解释） |

**三条判读纪律（写进正文，避免重复犯错）：**

1. **D1 必须连报分母 `d1_n`**。实测教训：某两批的 D1 从 **84.62% → 0.00%**，
   而根因是分母 **13 → 2**，不是接纳质量提高 ⇒ 只报比率会把"样本变少"读成"变好了"。
   并可核对：`S14B1` 与 `S14D` 的 `cost` 臂**逐步 `prefill_tok` 序列严格全等（292/292）**
   ⇒ 不是"回退到同一个控制器"的类比，而是**同一条执行轨迹**。
2. **"没有可行候选" ≠ "不发 prefill"**。控制器有两条降级路径：全无预测 ⇒ 回退阈值控制器；
   有预测但全超预算 ⇒ **取最省候选**。实测：某 run 的 D0 可行率仅 **5.4%**，而遥测显示
   **183/292 步仍在发 prefill**（step 0–2 = `prefill_tok=1024 fwd_ms=251.69`）
   ⇒ 从 D0 推"不发 prefill"是错的。旁证：该 run 的 cost 与 threshold 臂的
   **D2（26.71% / Σ624）与 TTFT 排队（8321 vs 8320 ms）几乎逐位相同**。
3. **prefill 的实际执行只能从遥测的 `note` 读**（该列不在汇总里）；
   缺失字段写"不可判"，**不得**当 0 —— 本项目在此踩过一次：
   遥测里没有 `tokens_prefilled` 这一列，把缺失读成 0 之后得出"没有可行候选 ⇒ 结构上无法发 prefill"
   这个**错误结论**（已撤回）。

## 6.6 实测：`ramp` 格（`P8FULL` / `S9AB`，`load_ramp`，全部 `MEASURED`）

轨迹：low 120 s @ λ=0.08 → high 90 s @ **λ=0.70** → recover 240 s @ λ=0.08（共 92 请求、450 s）；
持续容量由 high 段独立定稿 **C = 0.356 req/s**（6 个 run 极差 / 中位 **0.0%**）
⇒ λ/C = 0.22 / **1.96** / 0.22（即 high 段是**可持续过载**，不是"仍可服务的高负载"）。

**（a）污染机制在"负载水平连续变化"下同样出现，且可复现到步号（登记行 E10）**
3 个 adaptive run 的动作步号**逐位相同**：`[1216, 1240, 1264, 1288, 1312, 1336, 2432, 2456, 2480]`
（9 次，**全部是收缩**）；首次动作 `t = 123.0 / 123.1 / 123.2 s`（**high 段刚开始**），
**`queue_depth` 三个 run 都是 0**。触发读数 337.2 / 337.9 / 342.2 ms vs 同窗纯 decode
61.4 / 61.6 / 62.5 ms ⇒ **5.5×**；收缩把 `max_batched_tokens` 从 8192 压到 2048，
**纯 decode 步 `fwd_ms` p50 从 61/62/62 升到 118/118/118 ms（≈ +92%）**。

**（b）判据口径的干预实验（登记行 E12/E13，单变量 `signal_criterion`）**

| 臂 | 报告值 ÷ 同窗纯 decode | 达标率 | `tpot` p50 | `stall` p99 | 首次动作 |
| --- | --- | --- | --- | --- | --- |
| A（`tpot_p90`） | **5.47 / 5.47 / 5.73** | 0.1957 | 182.53 | **330.51** | t ≈ 123.0 s |
| B（`decode_p90`） | **1.33 / 1.33 / 1.32** | **0.2065** | 180.79 | **410.30** | t ≈ 131.2 s |
| 参照 `static` | — | 0.2174 | 175.9 | 412.4 | — |

⇒ **机制成立**（读数不再被污染，A 那批"纯 decode 还只有 61 ms 就收缩"的动作消失，
B 的首次动作触发值 138.0 **> 门限 129.6**，属**合法触发**），
但**净收益只有 +1 个达标请求**（18 → 19），且 B **放弃了 A 靠过度收缩换来的 stall 改善**
（"低 stall"本来就是把 decode 摊薄的副产品）⇒ 这是**权衡**，不是"换判据就更好"。
⚠️ **"改判据"只能消除*不该有的*动作，不能消除*收缩本身*的代价**：
B 仍会合法收缩，之后纯 decode 同样到 118 ms。

**（c）臂间对照不构成结论（`P8FULL`）**：static 达标率 `0.2174 ×3` vs adaptive `0.1957 ×3`、
达标吞吐 5.64 vs 5.08（**−10%**）—— 组内极差为 0（可复现），但**效应量只有 2 个请求 / 92**，
且是**进程内**重复；同时 adaptive 的 `stall p99` **低约 20%**（330 vs 412）而 `tpot` p50 高 3.7%
⇒ **是权衡不是纯损失**，登记为**待检验信号**。
⚠️ 且本批控制器**全程只朝一个方向动**（只收缩到边界、0 次放大）
⇒ 它是"单向棘轮"而非双向控制；**不能**据此说"控制器会振荡"。

**（d）静态响应面（登记行 E14/E15，`S10`，5 候选 × 3 轮）**：段级达标吞吐（tok/s）

| 格 | `chunk_size` | `budget` | low | **high** | recover |
| --- | --- | --- | --- | --- | --- |
| `ramp_static_c8` | 1024 | 8192 | 9.600 | 1.422 | 4.800 |
| `ramp_static_c8_ck512` | **512** | 8192 | 9.600 | **0.000** | 4.267 |
| `ramp_static_c8_ck2048` | 2048 | 8192 | 9.600 | 1.422 | **5.333** |
| `ramp_static_off_c8` | **off** | 8192 | 9.600 | 1.422 | **5.333** |
| `ramp_static_c8_bt2048` | 1024 | **2048** | 9.600 | 1.422 | 4.800 |

⇒ **静态最优集不随负载段迁移**（这是**否证**，不是"没测到"：迁移若存在，
应表现为"某段最优的 `chunk` 值不同"）；唯一明显的差异是**细分块在高负载段把达标吞吐打到 0**
（`ck512`：**0.000** vs 其余 **1.422**）⇒ "更小的 chunk"**不是单向更优**。
按预注册规则，Pareto 前沿 = {`ck2048`, `off`}（两者**逐位相同**，因为 prompt 恒 2048
⇒ `chunk_size = 2048` 的"分块"是**恒等操作**），平局取 `chunk.enabled = False` 优先
⇒ **`Best Static` = `ramp_static_off_c8`（不分块 / budget 8192）**。
⚠️ 该等价同时是一次**仪器一致性检验**（两个应当等价的配置给出逐位相同的数）——它通过了。
⚠️ 本条是**否证了一个假设**（"最优随负载迁移"），但它**不构成**"自适应无用"的证据：
本批只有静态臂，且 `ramp` 的 λ/C = 1.96 ⇒ high 段是过载。

# 7 系统收益与适用边界（阶段五）

> ⚠️ **不得预写收益**，也不得把"过载边界"当成"一般性能优势"（见 §6.1 的警告）。
> 本章目前的**唯一**已建立的结论是"**收益侧证据尚未产生**"，其余为骨架 + 占位。

## 7.1 三个负载区，分别解释

判定一个负载属于哪一区，用**静态臂**的实测（不是我们的假设）：

| 区 | 判据（静态臂实测） | 本文现状 |
| --- | --- | --- |
| **正常服务区** | 静态臂的 TPOT 分位明显低于 SLO | ⬜ 尚无数据 |
| **接近容量上限** | 静态臂的 TPOT 压着 SLO ⇒ 取舍最尖锐，也是自适应的**主要受益区** | ⬜ 尚无数据 |
| **过载区** | 各臂达标吞吐**全为 0** | ✅ 已测（`S14B1` `fixed` 格：四臂全 0；`S10` `ramp` high 段 λ/C = **1.96**） |

⇒ 本文已建立的只是**过载边界**：`fixed` 格上四臂达标吞吐全 0（静态臂 TPOT p50 = 156.0 ms > SLO 100），
`ramp` 的 high 段 λ/C = 1.96（**可持续过载**）。
⭐ 一条交叉印证：`ramp` 上 `ck512` 在 high 段的达标吞吐被**打到 0.000**（其余候选 1.422）
—— 这从另一个方向说明"分块大小"在这里不是单调更优的量。

⚠️ 与最接近方法（SLOWeave）的退化区间**同型**：它自述"**在无限过载下不保证无饥饿**；
持续过载时严格 TPOT 目标**可能没有安全的 prefill 预算**"。
本文的过载区观测与这一自述**相容**，但**不能**据此说我们刻画了它的边界——
我们只在自己这一平台上、用 λ/C = 1.96 单点观测到了它。

【待补·P13】三个区各自的边界（用哪个并发 / 速率划分）与逐区结论
（来源：静态臂的响应面 + `slo_reach`；当前状态：正常服务区尚无数据）。

## 7.2 与**公平**静态基线的对比

论文要能写"自适应优于**精心选择的**静态配置"，前提是对照**公平**：

1. 静态候选必须覆盖**自适应可用的同一组动作**（含 D1 选定的小 chunk，**并保留"不分块"对照**）
   —— 否则自适应会**独占新的可行动作**，比较失去意义；
2. 选静态最优的规则必须在**取数之前**冻结（本项目已经做过一次：`S10` 的支配 + 平局规则，
   结论是 `Best Static` = 不分块 / budget 8192）；
3. 静态最优必须在**同一模型 / 同一 SLO / 同一负载 / 同源码树**下重测（`S10` 的执行版本早于当前批次）。

⚠️ 一条**已更正的口径**（不要再用旧说法）：本项目此前把"静态基线只扫过一个点（1024）"
写进了多处限制条目 —— 该说法**已过时**。`S10`（15 次运行）已扫
`chunk_size` = **512 / 1024 / 2048 / 不分块** + 一个预算变体（`bt2048`）。
正确的说法是"**仍缺 1536 与小 chunk，且需审计旧结果对当前执行版本的适用性**"。

【待补·P14】公平静态基线的三点 / 五点结果（来源：D3；当前状态：依赖 D1② 的选定下限）。

## 7.3 独立运行验证

参数冻结后，用**未参与调优的轨迹**与**独立运行**验证；以**独立运行**为统计单位给出波动与区间。

⚠️ 一条已登记的**方法学限制**（**已由 n=5 复核并修正**）：`ramp` 是**开放环确定性**负载，
同一格 3 次重复在段级达标吞吐上**逐位相同**（极差 0）⇒ 它**不能**提供"置信区间"
意义上的波动估计；以独立运行为单位做统计，需要的是**含随机性的负载**或**参数扰动**
（本文尚未这样做）。

**【事实】** 该限制在 `S14B2`（`ramp`，4 臂 × **5** 重复全 `MEASURED`）上被复核，
结果**比原登记更细、也更该谨慎**——"极差 0"**不普遍成立**：

| 臂 | 达标吞吐 tok/s（r0–r4） | 极差 | `n_steps`（各重复） |
| --- | --- | --- | --- |
| `static` | 5.928 ×5 | **0.0** | 3736 ×5 |
| `cost` | 5.077 ×5 | **0.0** | 3572 ×5 |
| `threshold` | 5.362 ×4 + **5.363** | 0.001 | 3570 ×5 |
| `slo_weave` | 2.239 ×3 + **2.481** | **0.243** | **4886** ×4，**4201**（r4） |

**`slo_weave-r4` 的偏离是控制轨迹分岔、不是测量噪声**：其请求数、prompt/output 令牌量、
达标请求数四次**完全相同**（92 / 188 416 / 11 776 / 9），差异**只在控制器的步数**
（4201 vs 4886）与 chunk 终值（1 vs 4）。

**【解释】** ⇒ 三个后果：
1. **`ramp` 提供的是"4 次逐位相同 + 1 次分岔"，不是分布**。据此算置信区间无意义：
   任何区间都由那 1 个点决定。这与原登记的"极差 0 ⇒ 不可用"**结论相同、理由更准确**。
2. 该分岔与项目已登记的"自适应臂在门限贴工作点时跨重复不可复现"**同型**
   （见 §8 限制），因此它本身就是一条**可复现性**发现，而非需要剔除的异常。
3. ⚠️ 三段纪律：`slo_weave-r4` **不得剔除**；**不得**把 `2.481 > 2.239` 读成"该臂更好"；
   **不得**跨臂合并——各臂的"可复现性"**本身**就是结论。

⇒ **P15 的答案是方法学否定结论**：本文**未**建立"独立运行的置信区间"，
其障碍是**负载的确定性**（而非样本量），且该障碍在 `ramp` 上**已被量化**
（每臂 5 次重复中 4 次逐位相同）。要建立区间需要**含随机性的负载**或**参数扰动**，
二者本文均未做 —— 列入 §8 限制。

# 8 限制与负面结果

> 本节现在就能写：限制是**已知的**，不需要新数据。⚠️ 但**已登记缺陷清单**不在这里复述
> ——它在 `paper/failure_analysis.md` §4.7（含"已修 / 未修"状态），本节只写**对结论的影响**。

## 8.1 外推边界（最重要的一条）

本文全部证据来自**单卡 MTT S4000 + 单模型（Qwen2.5-7B-Instruct fp16）+ 自建迭代级执行器**。
因此：

* **不**声称跨平台普适；次平台（昇腾）的产物**不与本文并表**，也不作为本文结论的支持证据；
* **不**把 `host` 侧开销之类的量归因为**芯片固有机制**（它是本机 + 当前执行路径的量，
  含 python 侧打包 / mask 组装）；
* **不**声称"某个控制器在本文平台上更优"——本文的结论形式是
  **"预测可靠性由什么决定、失配怎样变成调度代价"**。

**单模型规模的明确后果**：本文**未做第二个参数规模**（裁决见 §7.4，2026-09-28）。
⇒ "机制在别的规模上是否同向成立"**未经检验**，本文**不据此做任何泛化主张**。
之所以列为限制而非补做：换模型必须**重采全部标定**（SLO 可达性 / 门限分离 /
成本形状，`README.md` §6），且成本模型**不得跨会话并表**
（`COST_PROFILE_S4000.md` 实测跨会话漂移 1.3–4%）——
即第二条规模不是"再跑一遍"，而是**再做一轮标定 → 重跑矩阵**。

**★ 环境绑定（2026-10-03 新增，会影响"哪些数字能进正文"）**：产物里的环境指纹
**不总是描述跑它的那台机器**。实测一例（`EXECOPT5`，10/10 份产物）：
`hardware_env` 写着 **2026-09-28**、容器 `…cf99469eb6…`，而该批实际跑在
**2026-10-03** 的容器 `…05264bbf0d…`。成因是共享指纹文件被"存在即用"地复用，
而**当时没有任何新鲜度或容器身份校验**。
⇒ 这条限制的用法是**划掉一类主张**：当"两批同环境"这句话**没有产物能证明**时，
**不得**把它当作已成立的前提（哪怕两批的数字看起来高度一致）。
现已实现修法（批次前置**重采指纹 + 校验容器/设备身份**），但**修法不补齐历史证据**
——历史产物的环境身份**保持未闭合**，按 §8.9 的分层处理。

## 8.2 `host` 项的适用范围

`host` 是"打包 / mask 组装 / 取回"等 python 侧开销，随**执行路径**与 **batch 上限**变化。
⇒ 换执行路径、改 `max_num_seqs`、改分块策略都要**重测**；
用旧的 host 表去判新路径的预算，会让判据偏松或偏严，而**不会报错**。
⚠️ 同一条边界也适用于**性能态**：设备有快 / 慢两档性能态（§3.3），
换测量协议（占空比）会拿到不同的绝对值 ⇒ **成本模型只能用同会话内对照**。

## 8.3 判据分辨率与"未判"

* **留出点 < 15 ⇒ 该格的判据只能记「未判」**（不许用 3 个点的 p95 说事）。
* **两次重复的稳健 CV > 10% ⇒ 先修测量**，不得进入对照比较。
* "未判"与"测出无效"**语义相反**，正文必须分开写。
* ⚠️ **n = 3 分不开"消除了某个机制"与"没抽中"**：本文实测到
  `P1S3B` 1/3 分叉、`P2` 0/3、`P1S3D` 0/3（合计 **1/9**）。
  ⇒ 可以说"已知的拒绝机制在构造上不再可能"，**不可以**说"跨重复可复现性已建立"。
  **别把"余量抬了一个量级"读成"问题已解决"。**

## 8.4 负载代表性

合成负载不代表所有生产环境：

* 长度分布为**均匀采样、无重尾** ⇒ 会**低估 P99**；
* `ramp` 的到达模型是**分段常量**（`piecewise`），不是真实流量的突发过程；
  因此"与最接近方法的差异点"只在"负载水平变化"这一维上被检验，
  **不覆盖**到达过程的突发性（SLOWeave 的 `bursty` 是两状态交替，与本文的连续 `ramp` 是**不同**的形态）；
* `fixed` / `ramp` 两格的 `n_failed = n_rejected = n_unfinished = 0` 是**负载产生不出**这些结局，
  不是"测过且没有"⇒ 不能据此声明"系统从不丢请求"。

## 8.5 闭模型的解释边界

闭环负载下，"计划到达时刻"恒为 0（真实时刻由执行器补位时分配）。
⇒ 引用到达 / 排队类指标时必须说明读的是**执行值**（`requests.jsonl` 的 `arrival_ms`）
而不是指纹里的计划值。本项目曾因此在三处文档里写下同一句错话（已更正）。
⚠️ 同源的一条：TTFT 的起点是**放行时刻**，不是"处理它的那一步的开始时刻"——
两者在长步下差别巨大（关闭分块时一步可达数百毫秒）。

## 8.6 负面结果（如实登记）

* **`fixed` 格上四臂达标吞吐全为 0**（`S14B1`，5 重复）⇒ 该格只揭示**过载边界**，
  **不能**支持性能优势；且静态臂反而有最高的吞吐（39.44 tok/s）与最低 TTFT（8132.7 ms）。
* **预注册的止损点已被触发**：秩保证划分下低估 p95 曾为 **6.12%**（阈值 5%），
  按覆盖率缺口补点后为 **9.02%** ⇒ "补覆盖"把**覆盖率**从 **53.57%** 提到 **100%**，
  但**没有**把拟合精度带上去。⇒ 本文不继续加密网格，改走"查表 + 保守回退"，
  并把覆盖率作为头部指标（`paper/failure_analysis.md` §4.2 事实 6/7）。
* **"最优点随负载迁移"被否证**（`S10`，`ramp` 三段）：静态最优集**不随段迁移**，
  唯一明显差异是细分块在高负载段把达标吞吐打到 0。
  ⇒ 这是**否证**（不是"没测到"），且它**不能**被读成"自适应无用"（该批只有静态臂）。
* **净收益远小于机制成立**：判据口径的干预实验（`S9AB`）使读数污染从 **5.5× → 1.33×**
  （机制成立），但达标率只从 **0.1957 → 0.2065**（**+1 个请求 / 92**），
  且代价是 `stall` p99 从 330.51 回到 **410.30**（≈ static 的 412.4）。
* **一处"看起来成立"实则不成立**：`S14B1` 的 cost 臂与 threshold 臂的 D2（26.71% / Σ624）
  与 TTFT 排队（8321 vs 8320 ms）**逐位相同**，根因是两者的**逐步 `prefill_tok` 序列全等（292/292）**
  ⇒ 它们**不是**两个独立的数据点，不能用来支撑"成本模型与阈值控制器行为不同"。
* **一处"高覆盖率"不蕴含"高精度"**：成本模型查表的**覆盖率与控制精度是两件事**，
  且**切分法本身能决定结论**（`costcalib_eval_v5.json`、`decouple_v3_v4.json`）。

  查表模型（五版标定，188 条记录）在**留出集上覆盖率 1.0（83/83，无一条落空）**，
  但其逐条相对误差 `abs_rel_p50` 仅 **2.06%**、`p90` **5.02%**、`p99` **11.41%**，
  且**低估率 66.3%**、**低估 p95 = 9.02%** ⇒ 预注册判据判 `model_holds = false`
  （阈值：低估 p95 ≤ 5%）。**覆盖率满分、判据不通过**——这两列必须并报，
  否则"覆盖了全部格子"会被误读成"模型是准的"。

  更关键的是**切分法决定结论**（`decouple_v3_v4.json`，同一模型、`modulus=2`）：

  | 网格 | 切分法 | 训练 / 留出 | 低估 p95 | abs_rel p90 |
  | --- | --- | --- | --- | --- |
  | 旧 | `hash` | 44 / 48 | **95.26%** | 90.79% |
  | 旧 | `rank_guaranteed` | 62 / 30 | **11.77%** | 7.17% |
  | 新 | `hash` | 60 / 64 | **95.26%** | 74.33% |
  | 新 | `rank_guaranteed` | 81 / 43 | **6.12%** | 5.77% |

  ⇒ **`hash` 切分下"模型完全不可用"（低估 95%），`rank_guaranteed` 下"勉强可用"（6–12%）**。
  即：**"成本模型是否成立"这个问题的答案，取决于留出集的切分方式**
  （`hash` 会把某些新出现的形状整片划到留出侧，模型从未见过 ⇒ 系统性低估）。

  ⚠️ 三条读法纪律：
  1. **不得**用"覆盖率 1.0"支持"模型准确"——两者是不同指标（见上）；
  2. **不得**只报 `rank_guaranteed` 的结果而不报 `hash`——这正是选择性报告的样子；
  3. 因此本文**不声称**"已建立可用的成本模型"，只声称
     **"成本模型的可用性对留出切分敏感，且覆盖率不构成精度证据"**。
     这是**方法学层面的负面结果**，也是 §6 中第三臂**至今不可用**的直接成因之一。

* **一处已撤回的错误结论**：遥测里**没有** `tokens_prefilled` 这一列，
  曾把缺失读成 0，得出"没有可行候选 ⇒ 结构上无法发 prefill"——**已撤回**。

* **★ 执行优化线的一条限定局部负结果**（`EXECOPT4` 3 轮 + `EXECOPT5` 5 轮，**两批独立一致**）：
  "常驻 KV 缓冲"这一机制在**它能被行使的样本**上是**净成本** ——
  尾段（**77 步**，单请求纯 decode，也是该机制的全部覆盖区）的 `pack` 总量
  **108.80 → 185.95 ms = +70.9%**（`EXECOPT5`，**5 轮逐轮配对比值的中位数**，**5/5 同号**）。
  ⚠️ **这是"限定实现与负载"的局部负结果**：只对**当前实现**（每步对整段 KV 做一次
  `copy_`）与**当前负载**（`short_chat` / 并发 8 / 64 请求 / `eager` / `max_num_seqs=32`）
  成立，**不得**外推为"该思想无用"或"搬运优化一定失败"。
  ⚠️ **两个口径必须并报**：`6.74%`（= 77/1143）是**前向组数量**覆盖率，**不是**耗时占比；
  尾段的**耗时**份额只有 **~0.52%**（加性核对残差 0.047%，88.6% 的全窗差来自尾段）
  ⇒ 全窗口的 **+0.37%** 是**算术后果**，既不能读成"几乎无影响"，也不能读成"不可分辨"。
  ⚠️ **已撤回的表述**："两臂 `fwd` 区间重叠 ⇒ 无差异 / 机制只作用在 `pack`"
  —— **区间重叠不是检验**，n = 5 下推不出"无差异"；本批只能记"**不足以判定 `fwd`**"。

* **★ 一类"自证文件变成新的遮蔽机制"的失效**（工具层面，2026-10-03）：
  为对抗"stdout 被沙箱垫片摧毁"而加的**旁路结果文件**，起初只记录 `setup`/`call`
  两个相位、**漏了 `teardown`**；而当时的判据允许"计数齐全 ⇒ 豁免非零退出码"
  ⇒ 实测（夹具收尾抛异常）真实 pytest 报 `1 passed, 1 error`，旁路报 `error=0`，
  **真实缺陷被读成通过**。
  ⇒ 该失效已修（逐相位记录 + nodeid 集合**双向对账** + 会话级异常），
  且**取消**了"按输出字符串自动豁免非零退出码"这条规则（它让任何能打印那句话的
  路径都能把自己的失败变成通过）。留在这里是因为它属于**方法学**层面的教训：
  **"看起来齐全"永远不是豁免依据**；任何用来证明某事的中间产物，都要问一遍

## 8.8 统计表述纪律（2026-10-03 新增）

本节不引入新数据；它规定**正文里那类比值该怎么写**，因为写错会让同一个量读数差 13 倍。

1. **数量覆盖率 ≠ 耗时权重**。二者不可互相代用：
   * **数量覆盖率** = 命中某机制的**前向组数** / 正式窗口前向组数（例：`77/1143 = 6.74%`）；
   * **耗时权重** = 该部分 `pack`Σ / 全窗口 `pack`Σ（同例：**0.5189%**）。
   解释"局部效应为什么在全窗口只剩一点点"时**必须用耗时权重**，否则会得出
   "稀释了十几倍"这类**算不出来**的说法。两者要并报。
2. **比值必须写明是哪一个统计量**：
   * **逐轮配对比值的中位数** `median(opt_i / base_i)` —— 消掉轮间整体漂移，问"同一轮内差多少"；
   * **两臂中位数之比** `median(opt) / median(base)` —— 不受轮内配对约束。
   本文实测两者可以很接近（+70.86% vs +70.91%）也可以不同（+0.37% vs +0.42%）
   ⇒ **不写清楚，别人复算会对不上**。
3. **区间重叠不是检验**。两臂的区间有重叠**不能**推出"无差异"（n = 5 更不行）。
   只能写"**本段不足以判定**"。
4. **中位数对差不可加**。`median(whole − tail) ≠ median(whole) − median(tail)`
   ⇒ 分解的加性核对是一个**诊断量**（本文实测残差 0.047%），不是恒等式。
5. **共同缺失 ≠ 相同**。两侧都空时 `{} == {}`、`None == None` 都恒真。
   任何 `==` 判据都要配一条"两侧都空"的反例，要求它**判失败**。

## 8.9 证据资格分层（2026-10-03 新增）—— 决定"哪些数字能进正文"

同一批产物里，**"数字是测出来的"（`data_label = MEASURED`）** 与
**"这批数字绑定了哪份代码、跑在哪台机器上"** 是**两件事**。
本文按下表分级，**只有 T1 能作为量化主张的直接证据**；
T2 只能用于**机制方向**判断，并须在引用处带上缺失项。

| 级 | 判据（都从产物现读） | 允许怎么用 |
| --- | --- | --- |
| **T1** | ① 源码身份闭合（`git_source` 可信 **且** `tree_digest` 可复算）**且** ② 环境身份闭合（实时机器标识 == 该批指纹描述的机器）**且** ③ 判据与口径已冻结 | 可作量化主张的直接证据 |
| **T2** | ①② 未同时闭合 | 仅**机制方向**与内部决策；引用须注明缺哪一条 |

## 9.1 结论

三条，逐条对应 §1.4 的贡献，且每条都带**具体量级**（不许写"显著提升"）。

1. **平台与执行特征**（§3）。在 **MTT S4000 单卡**上，本项目自建迭代级执行器的
   一步成本由**前向 + 一笔按序列的 host 开销**构成，实测 b8 一步
   **130.52 ms = 104.79 + 25.25 ms**；模型对**前向**是中位 **−4.4%**（准），
   对**整步**是 **−23.2%**。⇒ **"模型很准"与"判据偏松"可以同时成立**，
   判据必须写成"预测整步 ≤ 每步预算"，而 host 项是本机 + 当前执行路径的量（换路径必须重测）。
   另：快态平台（块 A）与服务协议（块 B）的差值随 prefill 增大（b1/pf512：
   **156.03 ms vs 166.85 ms**，取自设备侧探针 ⇒ **非 `MEASURED`**，只作平台特征）
   ⇒ 用快态最小值拟合 SLO 预测会**系统性偏乐观**。
2. **成本模型的失效与修复**（§4）。"留出误差"在**划分规则未固定时没有可比性**：
   同一个模型、同一份数据，留出低估 p95 从 **1.77% 变到 95.25%**；
   真因是训练集的**秩 / 覆盖不足**（该侧 `batch=8` 只剩纯 decode 点 ⇒ 设计矩阵 **秩 2 < 3**）；
   **秩保证划分**把同等规模下的误差从 **95.26% 降到 11.77%**；
   2×2 解耦给出 **划分规则 ≈ 89pp / 网格加密 ≈ 5.7pp**；
   **v1 网格在构造上达不到秩 3** ⇒ 扩网格是**必要条件**。
   满秩后仍 **6.12% > 5%** ⇒ 触发预注册的止损点，改走"查表 + 保守回退"，
   并把**覆盖率**作为头部指标——而"补覆盖"只把覆盖率从 **53.57% 提到 100%**，
   **没有**把精度带上去（低估 p95 **6.12% → 9.02%**）。
   "执行状态描述"那一半的性质**不同**：标定侧 `prefill_tok` 是"每条序列各做"、
   执行侧是"全步总量"，差约 **`batch` 倍**，且**不会因加密网格自愈**。
   【待补·P19】判据口径与标定语义两项修复的**净效果**（含连报的 `d1_n`；
   来源：`S14G`/`S14H`/`S14K`；当前状态：待跑）。
3. **失配到代价**（§6）。D1 给出"错误接纳"的直接证据：`S14B1` `cost` 臂
   **D1 = 84.62%（`d1_n` = 13）**，实例为"下一步实际 130.5 ms / 预算 120.0 ms / 预测 99.918 ms"；
   D2 显示保守等待集中在 `slo_weave` 臂（**53.27% / Σ队列·步 2352**）而静态臂为 **0 / 0**；
   D3 在 `fixed` 格上**四臂全为 0** ⇒ 该格是**过载边界**。
   在 `ramp`（`piecewise` 非平稳负载）上，控信号的污染机制复现到**步号**
   （读数 **≈ 5.5×** 纯 decode，触发时 `queue_depth = 0`），
   且收缩本身把纯 decode 步从 **61 ms 推到 118 ms（≈ +92%）**；
   换判据（`tpot_p90` → `decode_p90`）把该比值压到 **1.33×**，但净收益只有
   **+1 个达标请求 / 92**，代价是 `stall` p99 回到 static 水平
   ⇒ **机制成立、收益微薄**，且"静态最优集不随负载段迁移"被**否证**。
   【待补·P20】`slo_reach`（SLO 可达）负载上的 D3，即**服务收益**结论
   （当前状态：待设计并预注册）——**这是本文唯一尚未兑现的收益侧证据**。

**边界声明**（必须写在结论里，不是写在脚注）：全部证据来自
**单卡 MTT S4000 + `Qwen2.5-7B-Instruct` fp16 + 自建迭代级执行器**；
**不**声称跨平台普适，**不**把 `host` 之类的量归因为芯片固有机制；
本文**不主张**任何新的控制器算法，也**不主张**在本平台上优于最接近的方法
（SLOWeave 的机制已被实现为对照臂，而非本文贡献）。
